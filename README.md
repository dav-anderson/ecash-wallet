# ecash-wallet

One wallet library for PSP, ESP and FSP (Primary, Encumbered and Fast Service Points), with a thin command line. AIR apps embed the library, and its public functions are the product: the command line is one caller of them, and it only parses arguments and prints, so everything it does is a call into the library. A public function with no command behind it (`discard_purchase`, `clear_bad_proof`, `Wallet::snapshot`, `build_redemption`, `import_handoff`) is there for an app, and is tested through the library.

The library holds no BTC wallet. The app's own Bitcoin wallet puts the bytes from `build_psp_payload` in an OP_RETURN and pays.

## Status

Built and tested: the library, the command line and the end-to-end regtest runs in [REGTEST.md](REGTEST.md) (steps 0 to 49: purchase, claim, exchange, redemption, FSP, refusals, splitting, and key rotation). What each release contains is in [CHANGELOG.md](CHANGELOG.md). What is not built is in [ROADMAP.md](../sandbox-mint/ROADMAP.md).

## Setup

The wallet builds from GitHub as it is: `Cargo.toml` names mint-core at `v0.3.0` and `sp-wire` at `v0.7.0` (git tags), wire version 5; `Cargo.lock` is not shipped with this change and the build writes it. Through `sp-wire`'s `seal` feature the wallet gets the `air` crate. **It does not depend on the mint crates.** Every type it exchanges with the mints, the PSP payload and its encryption, the request hashes, the unit constants and the error codes come from `sp-wire` (see "Wire format and versions"). The mints (`psp-mint` `v0.9.0`, `esp-mint` `v0.11.0`, `fsp-mint` `v0.10.0`) are dev-dependencies only: the tests start real ones in the process, and nothing in the library or the command line links them.

sp-wire pins AIR at `eae5133` (AIR 3.0.0 plus the `SecretKey` export, on AIR's branch `air3-export-secretkey`) and air_server at `v1.0.1`, which takes `air` from crates.io; the `[patch.crates-io]` block in `Cargo.toml` points that at the same AIR commit, or two `air` crates are built and their types do not match (a patch applies only in the crate being built, so sp-wire's own block does not reach this one). To test against unpushed local copies of `sp-wire`, the mints or mint-core, `source ~/sandbox-mint/scripts/local-git.sh` points git at the local folders and their local tags.

```
cd ~/ecash-wallet
cargo test
```

The wallet makes no HTTP call, and there is no `http` cargo feature (the HTTP client and `reqwest` are gone; `reqwest` is a dev-dependency of `redeem_flow` alone, which calls the in-process ESP mint's operator routes). Every mint, the FSP mints too, is reached over AIR only, and there is no `air` feature to turn off: the library always builds sp-wire's `air-client`, which builds `air_server`. The `[patch.crates-io]` above keeps it on the same AIR.

A missing file is an empty wallet; a file that cannot be read is an error and is never replaced. **The file records the network it is for** (`network`: `main`, `regtest`, `signet` or `testnet`, the names of the per-network folders), and the wallet opens it only for that network: a new file is made with the network of the run, a file of another network is refused (naming both) and so is a file that records none, which a pre-release version wrote and this version does not read (start a new wallet file, or merge from a backup written by this version). Nothing is read from a refused file or changed in it. More in [DESIGN.md](DESIGN.md), "Notes and the wallet file".

## The PSP's calls over AIR

Six calls to the PSP go over AIR, and only over AIR. The first four are read-only: its **mint info** (what `wire_version` and `network` report, which the wallet asks before it sends anything to the PSP), its **keys**, its **keysets** and its **rotation window**. The other two have a body, and the first changes state: its **rollover** (the swap of old-keyset notes for new, sent by the rotation sync, on import of a handoff and on reclaim) and its **check-state** (`handoff check` and the check inside `handoff reclaim`). **`air.server` and `air.host` are required** (the DID is the SPI's: built in, or `air.psp_did`): the wallet writes a small sealed request into a mailbox of the PSP's DID on the configured AIR server and verifies the PSP's signed reply (the signature is the PSP DID key's, checked against the 33-byte DID alone). The reply body is the JSON the PSP's operator route used to return, so the wallet reads it with the types it already uses. Without the two settings every one of these calls stops with an error naming them. The PSP has no HTTP calls left in the wallet. The wallet's own files never go over AIR.

- **Where the calls are made.** The keys are read when the wallet builds a claim (`claim-psp` and every start that has a record to claim: the keys of the PSP mint's current keyset), and when it keeps notes on a live key set (`rotation_sync`, at startup and in `handoff reclaim`: the rotation window). The code that picks the way is `mint_info` (`psp_keys`, `psp_keysets`, `psp_window`, `psp_pickup`, `psp_claim`, `rotation_sync`, `reclaim_handoff`).
- **A purchase is a claim key, and what the PSP mint owes is a record the wallet reads over AIR; there is no paste.** `buy-psp --mint-key HEX` takes no amounts and builds nothing but a throwaway claim key of this purchase's own, made at random and never derived from or linked to the wallet's main DID, so the PSP mint cannot link two purchases of one wallet. The payload is that key's 33-byte public half (the claim DID) and nothing else, sealed to the PSP mint. The secret is saved in the wallet file (`claim_keys`) before the payload is shown, is kept like a PSP note (a backup carries it and a merge keeps it), and is never logged and never part of a handoff. When the payment has its confirmations the PSP mint writes an owed record for it to the SPI's AIR server (`air.server`/`air.host`), signed by its DID key and sealed to the claim DID, at an address only the wallet and the PSP mint can compute (`sp_wire::air_request::delivery`: the PSP mint's DID, the claim DID and an index). A claim DID that is paid more than once has records at index 0, 1, 2 and so on, in the order the PSP mint writes them. The wallet reads them in order, skips a cell that does not open (and says so) and stops at the first one that is empty, which it reads again at the next start. A record says the exact units the payment is owed (`due_units`, after every fee), how long it stays claimable (`window_secs`, 30 days) and how many claims the PSP mint counts for it (`max_attempts`). **The window of each record is counted from the wallet's first read of it**, because the PSP mint's write time is not visible to the wallet and is never later. A claim key is kept until the window of its last record has closed and no saved claim of it is waiting for an answer; a key with no record yet is kept for `psp.unpaid_key_days` (90 days by default) from `buy-psp`, then dropped with a warning that names the purchase the first time the pickup reads the AIR server and still finds no record (0 keeps it for ever). **Pay a payload within those days: a payment made after its key was dropped is kept by the PSP mint, and lost.** At the end the unclaimed records are reported lost, once, with their units, and the key is deleted at the start of any command. Every start, and `claim-psp`, reads the next empty cell of each key once; `claim-psp` also waits up to `--wait` seconds (60 by default) for a key that has no record at all. Reading the same cell twice changes nothing.
- **The wallet claims each record by itself (AIR kind 15, `PSP_CLAIM`).** There is no command for it besides `claim-psp`, which says what it did. At every wallet start, right after the records are picked up, the wallet builds a claim for each open record, at claim time and not at buy time: it reads the PSP mint's current keyset (rotation, kind 4) and its keys (kind 2), makes fresh blinded outputs that are powers of two and add up to `due_units` exactly (the binary digits of `due_units`, largest first), and signs the claim with the claim key over `ClaimRequest::digest(psp)`. It saves the claim, its bytes, its hash and the blinding factors with the record, together with the AIR request that will carry it, in one write before it sends anything. The PSP mint answers an accepted claim only: the wallet checks the answer (the keyset is the one asked for and its keys hash to its id, one signature per output in the claim's order, `issued_units` equal to `due_units`), stores the notes stamped with the keyset and the epoch of the set that signed them, and marks the record done in one write. Applying the same answer twice adds no notes. A **refused claim gets no reply**, so when no answer comes the wallet reads the PSP mint's current keyset again: if it is not the keyset the saved claim names (the keyset rotated between building and sending), it builds a new claim on the current keyset and sends that; otherwise it sends the identical bytes again (the PSP mint answers a repeat of an accepted claim from its stored answer, so a lost reply costs nothing). A claim the PSP mint ignores because its keyset is not current, is retired or is unknown does not use up one of the record's `max_attempts` at the PSP mint, and the wallet never builds more claims for a record than `max_attempts`. When every claim the record allows has gone unanswered the wallet tells you, once, that the PSP mint did not accept it and that the payment is lost at the date its window closes, and still sends the saved claim at each start in case it was accepted and its answer lost. Just before a window is closed the saved claim is sent one last time, identical: the PSP mint answers a repeat of a claim it took even after the deadline, so a payment whose answer was lost is settled by that last resend and is not reported lost. When that last resend cannot be sent (the AIR settings are missing, or the AIR server cannot be reached) the key is kept with its saved claim and the close is tried again at the next start. When the fees take the whole payment (`due_units` is 0) nothing is built or sent, and you are told once that the payment is lost. A note claimed on the current keyset is not rolled over by the rotation sync; only notes of a previous keyset are. Built and tested against psp-mint's real settlement; not yet run on regtest.
- **Pay a purchase's payload once.** A claim key is made for each purchase so the PSP mint cannot link your purchases. A second payment to the same payload is still owed to you and is claimed with the first (it is the key's next record), but it links the two. `buy-psp` prints this next to the purchase id: `Pay this payload once. Each purchase has a key of its own so the PSP mint cannot link your purchases; a second payment to the same payload is still owed to you and claimed with the first, but it links the two.`
- **Purchase size.** There is no minimum, and `buy-psp` takes no amount. The PSP mint's fees (two reads and one write) come out of what a payment buys, so a small payment can buy little or nothing and be lost. We recommend a PSP purchase of at least $5 (50 PSP). It is a recommendation: nothing enforces it, and `buy-psp` prints it. The setting `psp.min_purchase` (`ECASH_PSP_MIN_PURCHASE`) was removed in 0.8.0 and is refused with a message that says so. **A PSP note is valid if its amount is a power of two**: there is no largest note and no smallest. A PSP mint keyset has 64 keys, 1 to 2^63, and the wallet reads no largest note size from it.
- **What the signed reply adds.** The keys come in a reply signed by the PSP's DID key, so nothing in between, not the AIR server and not a man in the middle, can substitute keys.
- **No caching.** Every call asks again; nothing is remembered between calls except the run's first mint-info answer (below).
- **A PSP that cannot answer** (its mint lock is poisoned, a rotation step failed) says so in a signed reply, and the wallet fails at once with "could not answer keys now" instead of waiting out its tries.

- **The request is kept in the wallet file** (`air_requests`: the request kind, the request id, the one-off key, the slots written) from before the first write until it is answered, so a reply that comes while the wallet is not looking is read on the next call without writing a second request.
- **Retry:** 3 tries of 30 s (`air.attempts`, `air.reply_wait_secs`), the same request each time in the next free slot; then "the PSP did not answer over AIR" and the request stays. The next call of the same kind carries on with it (one kept request per PSP and kind).
- **A reply that fails a check ends the request** and says what was wrong: a network or wire version that is not this wallet's is the `Wire` error that names both numbers; a bad signature, another mint's, another request's, or a bad body is "a reply that was refused". A reply older than `air.max_skew_secs` when it is found is dropped and one new request is made in the same call.
- **The command line asks once per run** (the first answer is kept for the run): with the PSP down, AIR costs 3 x 30 s once, not at the startup check and again at the command.
- **Rollover and check-state.** The request JSON is the request body, sealed to the SPI's DID with the rest of the request (the notes in it are readable by the mint only), and the reply body is the JSON the mint returns. A signed refusal is the wallet error for a `400` refusal (`Refused`, `SpentElsewhere` with the positions), so a refused rollover is cancelled and its notes freed, and spent notes are marked,. A rollover sent again is **not applied twice**: the mint answers a body it has already answered from what it stored. The kept request is found by its body (its SHA-256 is kept with it), so the same rollover resumes and a different call never takes its place. The ceilings are the mint's ( 1 MiB and 1000 notes by default); a chunk of 1000 notes is about half a megabyte.
- **The built-in SPI DID is a PLACEHOLDER.** The wallet ships with the SPI's DID built in (`config::BUILTIN_SPI_DID`), and `air.psp_did` overrides it. The ESP has its own (below). Until the first SPI deploy puts the real one in (sandbox-mint OPERATIONS.md, "First SPI deploy", step 0) it is a point with no known private key: nothing sealed to it can be read and no reply from it can verify. It never passes silently: while it is in use the wallet prints a warning at every start and in `config`, and a call that fails says the DID is the placeholder.
- `ecash-wallet config` shows which way the PSP is asked.

## The ESP's calls over AIR

The ESP's wallet-facing calls go over AIR the same way as the PSP's, and only over AIR (`air.server` and `air.host` are required), to the ESP's own DID (`air.esp_did`, else the built-in one): its **mint info**, **keysets**, **rotation window** and **fees**, and the calls with a body, **rollover**, **exchange** and **redeem** (whose body is the canonical binary encoding). The ESP also answers a **transfer** (the service's swap of its own notes), but the wallet makes no such call: the service's ESP reaches it through `fsp issue`, `export-esp` and `receive`. The reply body is what the ESP's operator route used to return, so the wallet reads it with the code it already has. The ESP has no keys call (its keys arrive in the replies), and its `GET /audit` and `GET /health` are the operator's and the SPI's own, local to the ESP's machine: the wallet does not call them. The ESP's melts and burns with the PSP are between the two mints and are not the wallet's.

- **Two mints, two DIDs, one AIR server.** The PSP and the ESP each have their own DID (their own `mint_did_key.json`), and the same local AIR server and host can serve both, so one pair of settings serves both. A kind names a call, not a mint: the wallet sends the same kind (fees, say) to either DID and each answers in its own shape. Requests kept in the wallet file are found by DID, kind and body, so the two never meet.
- **The built-in ESP DID is a PLACEHOLDER**, like the SPI's: `config::BUILTIN_ESP_DID` is a point with no known key (and not the SPI's), replaced at the first SPI deploy. While either placeholder is in use the wallet warns at every start and in `config`, and an unreachable mint's error says which DID was the placeholder and which setting replaces it.
- **Sending an exchange or a redeem again is safe.** The ESP stores its answers by request hash, so a request resent after a lost reply gets the stored answer and is not applied twice. If the wallet crashes between writing the request and reading the reply, the next call finds the kept request by its body and reads the reply cell first.
- **Refusals.** A `400` is a signed refusal with the mint's JSON, read by the same code (`Refused` or `SpentElsewhere` for an exchange, `RedeemRefused` for a redemption; a redemption's `413` too), so a refused exchange is cancelled and its notes freed, as before. A `409` (the same request is being answered), a `413` on exchange or transfer or a `404` (rotation on a mint that does not rotate) come as refusals that carry `"http_status": N`; the wallet reads those as a plain mint error, never as a refusal of the notes, because the outcome may be unknown and the request is to be sent again. A `5xx`, the `502` of an ESP that cannot reach the PSP included, is a signed "cannot answer now".
- **Privacy.** A request is sealed to the ESP's DID with everything in it, so the notes in an exchange or redemption are readable by the ESP only, not by the AIR server; the reply is sealed to the wallet's one-off key. The size ceilings are the ESP's own, unchanged.
- **The ESP answers one request at a time** over AIR (in slot order), because an exchange talks to the PSP; a slow exchange holds up the requests behind it. The wallet's tries and waits cover this.
- **To get a working setup**, the ESP needs esp-mint's `air.*` settings and its DID key (`esp-mint pubkey` prints the DID to put in `air.esp_did`).

## The FSP mints' calls over AIR

A service's FSP mint (fsp-mint) is reached over AIR too, and only over AIR; the wallet has no HTTP client left. There is one mint for each service, so the wallet needs, for the service a command names, the **`air.fsp` entry** `<service DID>@<AIR server key>@<host>` (the DID the requests are sealed to and the replies are signed under, the AIR server the mint's own listener is on, and where it is). `fsp-mint serve` prints the entry when it starts. The calls are the kinds the ESP already has, mint info (1), keys (2), rotation (4) and fees (7), and two new ones, **FSP issue (11)** and **FSP spend (12)**, whose bodies are the JSON the mint's `POST /issue` and `POST /spend` took. A kind names a call and the DID picks the mint.

- **A service with no `air.fsp` entry is refused before anything is sent**, with an error that names `air.fsp`, `$ECASH_AIR_FSP` and the service. The same holds for `fsp sync` and `fsp-window`, and for the sync at startup, which logs the refusal for a service it has no entry for and tries again at the next start.
- **The reply body is the route's exact JSON**, with the same size ceilings. A `400` is a signed refusal with the route's JSON: an issue or spend that is refused is cancelled and its notes are free again, as before. Any other `4xx` is a refusal that carries `"http_status": N` and is a plain mint error (the outcome may be unknown; the request is sent again). A `5xx` is a signed "cannot answer now", the `502` of an fsp-mint whose ESP mint does not answer included.
- **A pending issue stays pending when the ESP mint does not answer fsp-mint.** The FSP mint says so in a signed reply, the wallet keeps the request, and the next `fsp sync` (or `fsp issue`) sends the same request: fsp-mint answers it from the answer it stored by request hash, so the ESP is transferred once and FSP is issued once. A spend is likewise found again by its notes.
- **The requests kept in the wallet file** (`air_requests`) are found by the mint's DID, the kind and a hash of the body, so a reply that comes while the wallet is not looking is read on the next call without a second request.
- **The wallet's records of the PSP, the ESP and every FSP mint are keyed by the service's DID in lowercase hex**, not by a URL.

## The key check

A mint that signs one user's outputs with a key it uses for that user alone (or gives one user a redeemable day nobody else has) can recognise that user's notes when they come back. So every mint publishes the keys it signs with on AIR, under its own DID, where every wallet reads the same bytes, and the wallet checks **before it stores anything from a reply** that each key the mint used is the key it published. The PSP and every FSP mint publish their key sets as a stream (a record for each key set); the ESP publishes a control stream (its maturity rule `m` and which key sets are live) and, for each day, the 64 keys of every service. The check is one function (`keystream`) at every place a reply is turned into notes: `finish_exchange`, `finish_fsp_issue`, `finish_fsp_spend`, `finish_rollover` (PSP and ESP), `finish_redemption` (refund and decline), `apply_claim` and `build_claim`. For a new ESP exchange it also checks the redeemable day: it must lie between the day of the first send plus `m` and the day of the reply plus `m`, widened by a fixed 300 s at both ends (not `air.max_skew_secs`), and the first send time (the wallet's clock: no app gives it) is saved in the wallet file before the first send and kept by a resend and a merge. A refund, a decline and a rollover keep the note's own day, so that window does not apply to them.

**What the wallet reads.** It reads only what it needs and asks the mint nothing: the latest record of each stream when it starts, the records after the last one it saved after a restart, and, for the ESP, the day of an exchange (today plus `m`) and the days of its own notes. It follows the stream of each mint it holds notes from or has a request pending with (a thread each, started by the first call to a mint, or earlier with `Wallet::start_key_feed`), and stops following a mint it has no business with. **Each followed mint costs one held read** on an AIR session of its own (the AIR server allows 256 held reads on a session, so the limit is not reached by key streams): the wallet needs one for the PSP, one for the ESP and one for each FSP mint it holds notes from, and a day read adds one while it waits. A mint's reply can come before its stream is written; the wallet then waits for the stream, up to a fixed 45 s (not `air.reply_wait_secs`), and reads once more before it decides; its reads of the streams take at least 10 s, however short `air.timeout_secs` is. A stream it cannot read yet, or a record not on it yet, is an error to retry, not a mismatch. **A record that never comes is.** When a record is still missing the wallet reads the mint's whole stream once (so a reply stored from more than two rotations back is still checked) and notes when it first missed it; the reply becomes a key check failure once enough newer records are on the stream (4 key sets for the PSP or an FSP mint, 2 control records for an ESP key set), or once a day has passed. **That day is fixed, as are the counts, the wait, the day slack and the least read timeout: no setting, variable or API field changes whether a mint is flagged** (only what is done about it, for an FSP mint: the blacklist settings below), and neither does a merged file: `merge` keeps this wallet's own key-check state and its own blacklist. With the mints' default rotation the day is what usually decides; an ESP day and an empty ESP control stream go by the day alone.

**On a mismatch** nothing from the reply is stored, the notes and the pending request are kept, and the wallet prints a warning on standard error that names the mint, what failed and the place, for example:

> WARNING: KEY CHECK FAILED at finish_fsp_spend. The FSP mint (DID …, service …) signed with KEY SET …, which it did not publish (it published …). Nothing from its reply was stored. Your notes and the pending request were kept. A mint that signs with keys other users do not see can recognise your notes when they come back. This FSP mint is NOT blacklisted (fsp.blacklist_on_key_mismatch is off).

**The blacklist is for an app developer who runs the wallet for its users, and it is off by default.** With `fsp.blacklist_on_key_mismatch` on, a failing FSP mint is blacklisted and its notes and requests are removed from the wallet (removed, not backed up); the wallet then sends that mint nothing and says why. Entries are in the wallet file and stay until they are removed by hand: `ecash-wallet blacklist list` and `ecash-wallet blacklist remove --service DID`. The SPI's PSP and ESP mints are never blacklisted; for them the check only warns. Not covered: the keys of notes received in a handoff or a hand-over (they are not a mint's reply), and a transfer's outputs, which no wallet check reads.

**A limit to know.** The check makes every user see the same keys; it does not make a mint honest about *who* it gives them to when a connection keeps reading the same few buckets of a large ESP day: a mint with many services splits its day record into buckets by a hash of the service DID, and a connection that keeps asking for the same bucket can still be recognised, less precisely than by a key of its own.

## Wire version

Every mint reports `wire_version` (every mint's mint info, over AIR; it is 5 since sp-wire 0.7.0, which changed the key set ID), and the wallet refuses a mint whose number is not its own (`WalletError::Wire`, naming both). The types come from [`sp-wire`](../sp-wire/README.md). Details in [DESIGN.md](DESIGN.md), "Wire format and versions".

## Command line

**Network.** The wallet is on mainnet unless given `--regtest`, `--signet` or `--testnet` (`--mainnet` may be given; at most one). Before it sends anything to a mint it asks the mint (its mint info, over AIR) which wire version it speaks and which network it is on, and stops if the mint is on another wire version or network or does not say; nothing is sent. Every walkthrough below passes `--regtest`. The wallet file is per network (see "Notes and the wallet file").

```
ecash-wallet [--wallet FILE] [--config FILE] [--regtest|--signet|--testnet] <command>
```

| Command | What it does |
|---|---|
| `buy-psp --mint-key HEX` | Makes the purchase's throwaway claim key (random, unlinked to the wallet's main DID) and saves its secret in the wallet file, then prints the encrypted payload as hex on standard output and, on standard error, the purchase id, the pay-once text, the payload's size with where to put it, and the recommendation of a purchase of at least $5 (50 PSP). It takes no amounts and asks the network nothing: nothing is built about the notes until they are claimed. `--sync` and `--reply-did` were removed and say so. |
| `claim-psp [--wait SECONDS]` | Reads the PSP mint's owed records for every pending purchase over AIR (cells 0, 1, 2 and so on, until the first empty one), waits up to `--wait` seconds (60 by default) for a purchase that has no record at all, claims each record (AIR kind 15) and says one line for each record: claimed N units, waiting (the claim is sent and unanswered, with the date its window ends), refused (the PSP mint did not accept it), or expired. Says which purchases were not read or not claimed, and exits with an error if any was not. It takes no signatures: `--file`, standard input and `BLIND_NONCE:SIGNATURE` pairs are gone. |
| `exchange --service DID --psp N [--amounts A,B,C] [--resume ID]` | Exchanges at least N PSP (N is 1 or more) for ESP bound to a service (its 33-byte AIR DID, 66 hex characters; the old 32-byte x-only form is refused with a message that says so). Whole PSP notes are spent and the difference comes back as ESP change. ESP notes are powers of two, so the amount and the change are each split into the fewest of them (`--amounts` picks other sizes, each a power of two, with the same total). `--resume` sends a pending request again. There is no command to split ESP you hold: convert it to FSP straight away (see DESIGN.md). |
| `receive FILE` | As the service: take the ESP that fsp-mint's `export-esp` wrote (a file per redeemable-after day, with the notes' spend secrets) into this wallet, so it can be redeemed. The file is read by sp-wire's `Handover::read`, which refuses a file that is not a hand-over, holds no notes, or has a note with no keyset (naming the note). This is its only use. The old `hand-over` and `transfer` commands are gone: FSP issue carries the ESP to the FSP mint over AIR. |
| `receive-psp FILE` | As the SPI's own wallet: take in the PSP that psp-mint reissued instead of burning (`revenue/<request hash>.json`, a `sp_wire::psp::PspHandover` with the notes' spend secrets). It goes the way a PSP handoff does: the file and its secrets are checked first (`handoff::check_psp_file`, no wallet and no network), then the notes against the key sets this wallet has seen and the notes it holds, stored in the balance and **swapped at the PSP mint** for notes only this wallet knows (`Wallet::import_psp_file`, then `complete_import`). The PSP is the wallet's own, `air.psp_did`: set it to the SPI's PSP. Prints `received N PSP in M note(s) (handoff ID, swapping at the mint)`, then the swap's result. The same file taken in again is refused (`handoff ID was imported already; nothing was added`) and changes nothing; a swap the PSP could not be reached for is sent again at the next start. |
| `--version`, `-V` | Prints `ecash-wallet VERSION`, then the `sp-wire`, `mint-core` and `air` versions `Cargo.lock` locked for this build, one `name version` per line. Reads no wallet and no settings. Build with `--locked` for the lines to be the ones used. |
| `balance` | PSP, ESP (by service and day) and FSP held, and what is waiting. A PSP credit the PSP owes for an overpayment is shown under the PSP total as pending, in PSP and USD (for example `10 PSP (1.00 USD) (pending)`), until it is claimed; it is not in the total. |
| `config` | The settings in use and where each came from. |
| `redeem --service-key-file FILE --memo TEXT [--max-bytes N]` | As the service, with the key read from FILE: redeem every mature free ESP note for that service (mixed days allowed) for a payout to TEXT. Reads the rate and ceiling from the ESP's fees (an AIR call), prints each request's size and fee, splits over the ceiling (`--max-bytes` only lowers the mint's; a ceiling too small for one note is refused and names `--max-bytes` or the mint's, whichever applies; the summary line comes before any `not sent` line), and on `refund_required` or `outputs_over_limit` rebuilds from the mint's totals and sends again. |
| `redeem --service-key-file FILE --resume ID` | Send a pending redemption again after a lost reply or fault. |
| `redeem --collect` | Ask about every redemption waiting for payout: completed ones end, declined ones give back the reissued notes with the reason. |
| `fsp issue --service HEX [--esp UNITS \| --psp N]` | Issue FSP from this wallet's free ESP for the service (all of it if no amount). `--service` is always needed, for `fsp pay` and `fsp sync` too; there is no default (`storage.wallet` is the wallet-backup list, not the service FSP is paid to), and without it the command refuses. |
| `fsp pay --service HEX --units N [--memo TEXT]` | Pay N FSP units to the service, with change. If the mint says some of the notes are already spent, those notes are marked spent (they leave the balance) and the rest are freed, so the next `fsp pay` does not pick them again. |
| `fsp sync --service HEX` | Finish pending FSP requests and roll previous-keyset FSP over now (it also happens on every connection and at startup). |
| `fsp-window --service HEX` | Print the FSP mint's rotation schedule (an AIR call, kind 4). |
| `handoff export-psp --to DID --psp N [--out FILE]` | A **PSP handoff**, a developer to a user (for example after an in-app purchase): take free PSP notes adding up to exactly N out of this wallet and print them as one string (`SPHP2:...`), sealed to the recipient's DID public key `DID` (66 hex characters), so only the holder of the matching secret key can open it. It carries PSP only, never a DID key or FSP. The warning and the size go to standard error. See "Handoff between wallets". |
| `handoff export-fsp --fsp SERVICE:UNITS... --did-key-file FILE [--out FILE]` | An **FSP handoff**, to your own new device: a little FSP (enough to pay to fetch your wallet from the AIR) and your DID secret key from `FILE` (64 hex characters; a file that group or others can read is refused, with `chmod 600 FILE`), as one string (`SPHF2:...`). **Not encrypted**, because it carries the key it would be encrypted to: anyone who sees it can spend the notes and act as your DID. |
| `handoff import STRING\|FILE\|- [--did-key-file FILE] [--did-key-out FILE] [--from NAME]` | Take a handoff in; the kind is read from its start. Checks it, refuses one imported before and the old `SPH1:` kind, and records where the notes came from. A PSP handoff needs `--did-key-file` (the secret key of the DID it was sealed to; owner-only, as for `export-fsp`). Its notes are **in the balance at once** and are **always swapped** at the PSP mint for notes only this wallet knows, now and at every start while the mint cannot be reached (`balance` shows how much is still unswapped). An FSP handoff is **never swapped**; its DID key is written to `--did-key-out` (`0600`, never replaced) and is refused without it. |
| `handoff check ID` | Ask the PSP mint where a PSP handoff you made stands, from its record of which notes are spent: **none** (still yours to reclaim), **all** (the receiver swapped or spent them: the handoff is done) or **some** (those are dropped from the record, the rest can be reclaimed). |
| `handoff reclaim ID` | Take back what is left of a PSP handoff the receiver has not swapped: swap the notes back to this wallet at the mint, for fresh notes only it knows. The mint takes whichever of the two swaps reaches it first; if the receiver was first, the handoff is recorded as done and nothing comes back. Run it again after a crash or a lost reply. |
| `handoff list`, `handoff cancel ID`, `handoff done ID` | The handoffs made and imported. `cancel` puts an unclaimed handoff's notes back **without asking the mint** (use `reclaim` for a PSP handoff). `done` drops them once you know the other wallet has swapped. |
| `merge FILE` | Merge a wallet file retrieved from storage into this wallet (see "Merging two copies of a wallet"). |
| `esp-schedule [--by YYYY-MM-DD]` | ESP mature now, mature by the date, and by month, from the wallet's notes (all services). |
| `blacklist list`, `blacklist remove --service DID` | The FSP mints this wallet blacklisted after a failed key check (see "The key check"): who, when, where and what failed; and the only way off the list. Neither makes a call to any mint. |

No mint has a URL: the PSP and the ESP are reached over AIR through `air.server` and `air.host`, and a service's FSP mint through that service's `air.fsp` entry. `--psp-url`, `--esp-url` and `--fsp-url` (and `$ECASH_PSP_URL`, `$ECASH_ESP_URL` and `$ECASH_FSP_URL`) are gone. The wallet's records of the PSP and the ESP (their live keysets, their swap times, and the mint a PSP handoff names) are kept under their DIDs in lowercase hex, as an FSP mint's are, and a PSP handoff names the PSP by its DID and nothing else: the reader refuses a URL, a name, another DID or capitals with `Invalid`. A record kept under an old label is not read or migrated.

`--service-key-file FILE` names a file that holds the service's secret key as 64 hex characters, the same file as fsp-mint's `service_key.hex`. The key is never typed on the command line, so shell history and the process list never hold it. A file that group or others can read is refused, with the reason and `chmod 600 FILE`. There is no `--service-key` flag.

## Handoff between wallets

A handoff moves notes from one wallet to another as one string, with no AIR, mint or network in between (a QR code works too: see below). There are exactly two kinds. The API, the command line and the string format make every other mix impossible, and a hand-made one is refused.

| | PSP handoff | FSP handoff |
|---|---|---|
| For | a developer to a user, after an in-app purchase | one person's old device to their new device |
| Carries | PSP notes only | FSP notes and the DID secret key |
| Encrypted | always, to the recipient's DID public key | never (it carries the key it would be encrypted to) |
| On import | in the balance at once, and always swapped at the PSP mint, no opt-out | never swapped |
| Taken back | `handoff reclaim` (the mint decides who wins) until the receiver swaps | `handoff cancel` (local only) |
| Starts with | `SPHP2:` | `SPHF2:` |
| Made with | `handoff export-psp --to DID --psp N` | `handoff export-fsp --fsp SERVICE:UNITS --did-key-file FILE` |

The old combined `SPH1:` handoff of 0.4.0 (PSP, FSP and an optional key, swapped only if asked) is refused with a message that names the two new kinds.

**PSP handoff.** The notes' spend secrets are sealed to the recipient's DID key with `sp_wire::seal`, which is AIR's own `PublicKey::encrypt` (no new cryptography). The app makes its DID locally and tells the developer's service the public key; the service runs `export-psp`. The user's wallet opens it with the DID secret key, counts the notes in its balance, and swaps them at the PSP mint first thing, whenever the mint can be reached (AIR kind 5, same amounts): on import, then at every start and on every connection to the mint. The handoff is final for the receiver when the swap succeeds. If the mint cannot be reached, the notes stay **unswapped**: they are in the balance and can be spent, `balance` prints how much of it is still unswapped, and the swap is sent again at every start. There is no lock on unswapped notes, because none is needed: spending a note at the mint burns it exactly as the swap does, so whichever reaches the mint first wins and the other is told the note is spent. A swap whose notes were spent meanwhile is rebuilt for the rest. If the mint says a note was spent already (the sender reclaimed it, or a copy was received first), that note leaves the balance and the user receives nothing for it.

**Reclaim.** While the receiver has not swapped, the sender can take the notes back with `handoff reclaim ID`, and `handoff check ID` says where it stands. Both ask the PSP mint's record of which notes are spent (AIR kind 6), and the mint decides who wins: a reclaim is a swap of the same notes back to the sender, and the mint takes the first swap that reaches it and refuses the other with nothing burned. All notes spent means the receiver has them (the sender gets nothing, and the handoff is done); none spent means the sender can still reclaim; some spent means those are gone and the rest can be reclaimed (or swapped by the receiver: first to the mint wins). The stored swap is sent again after a crash, and the mint answers a repeat from its record. An FSP handoff has no reclaim: the mint has no record of who holds an FSP note.

**FSP handoff.** For a user setting up a new device that holds nothing yet: the old device hands over the DID key and just enough FSP to pay to fetch the wallet from the AIR. Both devices are one owner's, so nothing is swapped. After the fetch, run `merge FILE` on the wallet you fetched: the small wallet from the handoff and the full one are united, net of the FSP spent on the fetch. The AIR fetch does not exist yet, so the merge is a separate step that runs after it. A merge takes no key-check state from the other file (what it read of the mints' key streams, when it first missed a record, when it first sent an exchange): the wallet keeps its own and reads the streams itself.

**Both strings are bearer secrets**, and an FSP handoff is worse: it also holds the DID secret key and is not encrypted. Hand it over in person or by QR code between your own devices, never post it or send it over a network, and delete it once it is imported. The warning is printed on standard error on every export and every import (`PSP_WARNING`, `FSP_WARNING`).

Reclaim, cancel and done: the notes leave the sender's balance when the string is made. For a PSP handoff, `handoff reclaim` brings them back through the mint, which is the safe way. `handoff cancel` puts them back locally, without asking the mint; if the other wallet already has the handoff, the first of the two to swap or spend wins, so cancel is for a string that was lost or never delivered, and for an FSP handoff. `handoff done` drops the sender's copy once it knows the handoff was claimed.

Size, for the QR code: about 254 + 150 × N characters for a PSP handoff of N notes of one key set (the PSP is named by its 66-character DID, and the seal adds 80 bytes), and about 233 + 150 × N for an FSP handoff of one service (the key adds 32). One QR code in alphanumeric mode holds about 27 notes at error correction L, or 21 at M. More than that goes in a file (`--out`). The wallet draws no QR code. Pipe the string to a tool: `ecash-wallet handoff export-psp --to DID --psp 5 | qrencode -t ANSIUTF8`.

**`send-psp` is gone.** `send-psp`, `sent` and the `psp1` token are removed (`receive-psp` is now a different command: it takes in the file psp-mint writes for the SPI's wallet, see the table); the PSP handoff does the same job, sealed to one DID, with the reclaim and check brought over from `sent --reclaim` and `sent --check`. The commands now print a message naming their replacements. **Old records are not read:** the wallet no longer reads the `sent` list of a file written by 0.4.0 or earlier, and a file that holds a combined handoff does not open. Reclaim or settle such records with the 0.5.0 build first. Purchases still open in a 0.7.x file (`pending_purchases`) are not read by 0.8.0 either: settle them with 0.7.2 first. A `psp1` token string can no longer be imported: ask the sender to reclaim it and send a handoff.

## Merging two copies of a wallet

`merge FILE` merges a wallet file retrieved from storage (an AIR backup, a copy from another device) into this one. Notes are united by identity, a note spent or handed off in either copy stays gone, pending requests are united without duplicates, and the wallet file's `version` counter goes up with every change. Both copies must be of one network: a copy of another network is refused, naming both, and so is a file that records no network; this wallet is left as it was. Details in [DESIGN.md](DESIGN.md), "Handoff, merge and the service ID".

## Tests

```
cargo test --all-features
cargo fmt --check
```

`cargo test --all-features` also runs the tests that need the mints' AIR listeners: every wallet test of a call to a mint goes over AIR (there is no HTTP form of those calls left), against an `air_server` started in the test process (on port 5702, which the AIR client always dials, so the port must be free; the tests in one binary take turns) and the real listeners of psp-mint and esp-mint. `tests/psp_delivery.rs` is the pickup: a paid purchase settled, delivered and read with no paste, two payments to one claim key read in order, a cell that does not open skipped, the AIR server down at settlement and a later retry delivering exactly one record, and the message when the AIR settings are missing. `tests/psp_claim.rs` is the kind 15 claim against psp-mint's real settlement and claim desk with the fees on (what is due split into powers of two, a resent claim counted once, two records on one key, the last resend before a window closes, a window that closes unanswered, a keyset race, and what a handoff and a backup carry). `tests/air_flow.rs` is the PSP's mint info, keys, keysets, rotation, rollover and check-state, with a request resent and not applied twice, refusals, a tampered or wrong-kind reply, a PSP that cannot answer, no call made when `air.server` and `air.host` are missing, and the placeholder DID. `tests/esp_air_flow.rs` is the same for the ESP (a stand-in PSP for the exchange): mint info, keysets, rotation, fees, rollover, exchange and redeem, refusals (and the `409`, `413` and `404` that are not refusals). `tests/flow.rs` is a purchase from payload to notes and an exchange for ESP, the exchange sent over AIR to esp-mint's real listener. `tests/redeem_flow.rs` also takes the ESP that fsp-mint kept through `export_esp`, a service wallet's `receive_handover` and a redemption. `tests/redeem_flow.rs`, `tests/rotation_flow.rs`, `tests/fsp_flow.rs` and `tests/handoff_flow.rs` run the redemption, key-rotation, FSP and handoff flows the same way (the FSP tests use fsp-mint's `AirIssuer` against esp-mint's real listener, and the wallet's own calls to the FSP mint go to fsp-mint's real AIR listener on the same `air_server`). These use `air_listener` (psp-mint, esp-mint) and `AirIssuer` (fsp-mint), and are built only with the `air-listener-tests` feature (`--all-features` has it); plain `cargo test` skips them and runs the unit tests, `cli` and `keyset_refusals`. The key check is tested where it is made (`src/keystream.rs`: the pure checks, the day window and skew edges, the blacklist on and off, the cap, the PSP and ESP that only warn; and the `finish_*`, `apply_claim` and `build_claim` sites in `src/esp.rs`, `src/rotate.rs`, `src/psp.rs`, `src/redeem.rs` and `src/handoff.rs`) and end to end against real mints, whose test listeners publish their streams after every request they answer: a PSP or FSP mint can be told to publish one key changed or to hold its stream back (`tests/fsp_flow.rs`, `tests/air_flow.rs`), and an ESP's stream can be written by hand (`tests/esp_air_flow.rs`, `tests/redeem_flow.rs`).

The tests run in one process with real mints (psp-mint, esp-mint and fsp-mint are dev-dependencies at their release tags) and no network. What they cover is in [DESIGN.md](DESIGN.md), "Tests".
