# ecash-wallet: design notes

How the wallet library works and why. The README has the build, the settings, the command line and the tests; this file has the reasoning and the behaviour of each call. The sections were moved here from the README without changes except where noted in [CHANGELOG.md](CHANGELOG.md).

## Wire format and versions

The request and response bodies, the PSP payload and its sealed form, the key-set ID, the request hashes and digests, the redeem encoding, the unit constants and the error codes are defined in the `sp-wire` crate, shared with the mints, so the wallet cannot drift from a mint by a byte. What stays here is the wallet's own: the note file, coin selection, blinding, the schedules and the command line. Two small things are the wallet's own copies and are not wire format: the date parser for `esp-schedule --by` (`src/date.rs`), and the assumed redemption fee rate and request ceiling used before `GET /fees` has been read (`src/redeem.rs`).

Every mint reports `wire_version` and its network in its mint info, an AIR call (kind 1) that all three kinds of mint answer. `mint_info::verify_psp`, `verify_esp` and `verify_fsp` read it, along with the network, before anything is sent, and refuses a mint that reports another number or none: `WalletError::Wire`, which says the mint's number and the wallet's and to update whichever is older. The command line calls it for every mint. **Changing any encoded byte or JSON field in `sp-wire` means bumping `WIRE_VERSION`.**

## Notes and the wallet file

Each note is stored with its spend key, its amount and its terms (an ESP note has a service and a redeemable-after day). The notes, and the requests that have been sent and are waiting for a reply, are one JSON file:

- `--wallet FILE`, else `$ECASH_WALLET_FILE`, else `~/.ecash-wallet/<network>/wallet.json` (`main`, `regtest`, `signet`, `testnet`, from the network flag). *Why per network:* notes of one network are worthless on another, and one file for all of them made it easy to send regtest notes to a mainnet mint.
- **The file records its network.** `WalletData::network` is required and is one of `main`, `regtest`, `signet`, `testnet`: the strings the command line uses (`network()` in `main.rs`) and the names of the folders above. It is a string because the library links no mint crate, and so has no network type of its own to use. `Wallet::open(path, network)` takes the network the wallet is opened for. A missing file is made with it. A file of another network is refused with `WalletError::Invalid` naming the file and both networks. A file with no `network` is refused with `WalletError::Corrupt`, saying it was written by a pre-release version, that there is no compatibility for it, and that the user can start a new wallet file or merge from a backup written by this version. A refused file is not read into the wallet and is not changed. *Why:* a path is all that tied a file to a network, so `--wallet FILE`, a copied file or a backup could be opened on the wrong one, and notes of one network are worthless on another. The check is on the file, before any mint is asked (the mint's own network is checked against the run's, at every connection, as before).
- It holds spend keys, so it is created with `0600` permissions.
- Every change is written to a temporary file, fsynced and renamed over the old file, and the directory is fsynced. A change is saved before the call that made it returns. In particular `build_psp_payload` and `build_exchange` save the blinding factors before they hand out the bytes or the request.
- A missing file is an empty wallet. A file that cannot be read is an error and is never replaced.
- The file has a `version` counter (up by one on every write), departure and return counters for notes, a set of finished request ids, and the handoff records. They are what lets `merge` reconcile two copies; see "Handoff, merge and the service ID". In a new file they start at zero and empty.
- Moving the note store into the AIR is deferred. The file is a development placeholder.

Losing the file loses the notes and the blinding factors for anything in flight.

## Library

### PSP

```
build_psp_payload(outputs, mint_did_pubkey) -> PurchaseBuild { id, payload }
apply_delivery(purchase_id, outcome) -> Delivered
mint_info::psp_pickup(wallet, air, wait_secs) -> Vec<PickedUp>
```

`build_psp_payload`:

1. Takes the note sizes in PSP (powers of two, at most 255, each no larger than the PSP's largest note once the wallet has read it; a PSP is $0.10, so 10 PSP are $1).
2. Makes the purchase's own one-off reply key (`sp_wire::seal::SecretKey::new()`) and blinds each output with a fresh spend key and blinding factor.
3. Encodes the payload with `sp-wire`'s `payload::encode` (the reply key's 33-byte public half as the reply DID, then each amount and blind nonce).
4. Encrypts it to `mint_did_pubkey` with AIR's secp256k1 encryption (`sp-wire`'s `seal::encrypt`).
5. Saves the pending purchase (the blinding factors, the spend keys, the reply key's secret and the delivery id), then returns the bytes. The key is on disk before any payment can be made.

`id` is the SHA-256 of the sealed payload. The **delivery id** (`PendingPurchase::delivery_id`) is the SHA-256 of the *unsealed* payload under `sp-psp-purchase-v0` (`sp_wire::air_request::delivery::purchase_id`): it is what the PSP sees after it opens the payload, which a seal (randomised) and the txid (unknown to the wallet) are not.

**Delivery.** The PSP writes one record per purchase to the AIR server at an address derived from its DID, the reply DID and the delivery id; the record is a reply envelope signed by the PSP's DID key and sealed to the reply DID, whose body is the signatures and the PSP's live keysets, or that the payment is held, or a rejection's reason, the last two with what the PSP received and `open_until`. `psp_pickup` computes the address of every pending purchase that has a key, reads them all in one connection (held, so a record that arrives while it waits is returned, under one deadline), opens each with the purchase's key, checks the PSP's signature and that the record answers this purchase, and calls `apply_delivery`. A record that fails a check is that purchase's `Pickup::Bad` and changes nothing; the others are still picked up. A record has no freshness limit: it can be read days after it was written.

`apply_delivery` is all or nothing. For signatures it checks that the record carries the keys of the keyset that signed (and that they hash to the keyset id), matches each pair to a pending output by blind nonce, unblinds it and stores the note; a pair that matches no pending output, or an amount the keyset has no key for, changes nothing. The purchase is then cleared, including the outputs the PSP did not sign (a payment short by more than the price tolerance: the PSP keeps their value, the record says how many units). A held or rejected record does not clear the purchase: it is marked open (`PendingPurchase::open`, an `OpenPurchase` with the kind, the reason, what was paid, and `open_until`) and `Delivered::Open` returns it. The purchase keeps its blinding factors and its reply key, because the PSP may settle it (a corrected request or a credit, not designed yet). The bitcoin that was paid stays with the PSP, and if the purchase is not settled by `open_until` the PSP forfeits it. The same record again, on an open purchase, is `AlreadyDone`; a `Signed` record on an open purchase is applied as usual. A record that names no window gets the wallet's own, 14 days from when it is applied. A purchase that is no longer pending returns `AlreadyDone` and writes nothing, so applying the same record twice changes nothing.

**The key outlives the notes when something may still be owed.** The reply key is deleted with the purchase unless the record says the purchase may still be open: the PSP owes a credit (`credit_cents > 0`), or some requested output was neither signed nor reported as dropped. Then the secret moves to `open_replies` (`OpenReply`), because the credit is claimed with a reconciliation request signed by the same key (see "Reconciliation" below); the key is kept until the claim is answered or the window closes. **Closing.** `Wallet::close_expired(now)` deletes every open purchase whose `open_until` is `now` or earlier, with its blinding factors and key, and every `open_replies` entry past its `open_until`; it writes nothing when nothing is due. The command line calls it when any command starts, before the pickup, through `mint_info::psp_close_expired`, which first sends each payment's saved request one last time (see "Reconciliation"). The window is the PSP's, read from its record, and `now` is the wallet's clock: the PSP forfeits at `open_until` by its clock, so a wallet clock that differs closes a little early or late. A purchase with no record yet is never closed by the clock: the payment may not have been made. `psp_pickup` does not read an open purchase again (`Pickup::StillOpen`): the record is write-once, and what settles the purchase is a reconciliation request (below). `close_expired` returns one `Loss` per payment it gave up, and `Loss::forfeited()` says plainly that the PSP forfeited the payment and the funds are lost, with the amount. The key is never part of a handoff. A purchase made before this change has no key (`Pickup::NoKey`): it cannot be picked up, and `discard_purchase(id)` (library only) drops a purchase that was never paid.

### ESP exchange

```
build_exchange(psp_units, service, esp_amounts) -> ExchangeBuild { id, request }
finish_exchange(id, response) -> FinishResult
cancel_exchange(id)
```

The mint's exchange is exact, and the smallest exchange is 1 PSP ($0.10, 10^11 ESP), set by the mint's `exchange.min_psp`. So `build_exchange` always asks for the full value of the PSP notes it spends. It picks PSP notes with the smallest total that is at least `psp_units` (exactly `psp_units` whenever some set of its notes adds up to it). The amount asked for becomes the service's ESP notes: `esp_amounts` splits it (default one note of `psp_units * 10^11`, which fits up to 184,467,440 PSP). Anything the chosen notes are worth beyond `psp_units` is added as extra ESP notes under the same terms (the same service and redeemable-after day), so the request always matches. That change is ESP, not PSP, and cannot be turned back into PSP, which is why the wallet looks for the tightest cover. It signs every PSP input over the exchange memo and reserves the notes. `ExchangeBuild` reports `psp_spent` and `change_esp`, and `FinishResult` reports `change_esp`. `finish_exchange` unblinds the mint's reply into ESP notes, each with the service and redeemable-after day, and removes the PSP notes that paid for them. `cancel_exchange` frees the reserved notes, and is only safe when the mint refused the request. After a timeout or a fault, send the same request again: the mint stores its answers by request hash.

`mint_info::psp_keys(wallet, air)` and `mint_info::send_exchange(wallet, air, &request)` make the two calls, both over AIR. A `400` is `WalletError::Refused`. Nothing was burned by the request, with one exception: `NoteSpentElsewhere` means that on a retry the ESP mint found some of its PSP notes spent under another memo (the holder spent them somewhere else), and signed nothing. The `400` body names those notes. `esp_replies::exchange_refusal` reads it into `WalletError::SpentElsewhere { why, inputs }`, and `mark_spent_elsewhere(id, inputs) -> SpentReport { marked_spent, freed }` drops the pending exchange, moves the named notes out of the wallet's notes into a record of spent notes (`spent_notes()`), which the balance does not count and exchanges cannot pick, and frees the request's other notes. It changes nothing if the mint names no note, or a position the request does not have. See the esp-mint README, "Burn memos". Anything else that goes wrong is `WalletError::Mint` (the outcome may be unknown).

**Why there is no ESP split.** Only the named service can move an ESP note, so a holder cannot split one, and a payment is a set of whole notes that adds up exactly (see "The service takes in ESP"). A way for the holder to split an ESP holding was considered and is not built. A holder converts ESP to FSP straight away, and the FSP mint splits and makes change, so ESP notes are not kept long enough for their sizes to matter. The sizes that do matter are chosen when the ESP is made: exchange in the sizes you will pay (`--amounts`, each a power of two). See esp-mint's DESIGN.md, "ESP amounts are powers of two".

**Why there is no rebuild after a lost wallet file.** The blinding factors of a PSP purchase exist only in the wallet file, so with the file lost the signatures cannot be turned into notes. A way to rebuild is not built, because the AIR keeps the wallet's storage redundant; the local file is a development stand-in (see the ROADMAP).

### The service takes in ESP

```
receive_handover(&handover) -> (count, units)
```

An ESP note names one service, and only that service can redeem it or move it. **How the service gets its ESP.** A holder pays a service with FSP, and `fsp issue` hands ESP to the service's FSP mint over AIR (`fsp.rs`: the notes with their spend secrets, in an issue request, and the wallet keeps the `Handover` it sent in `handovers` as a record). The FSP mint keeps the ESP, and its `export-esp` writes it to files, one per redeemable-after day, for the service's wallet to take in with `receive` (`receive_handover`) and `redeem`. `receive_handover` checks that each spend secret matches its note's nonce, refuses a note the wallet already holds, refuses a note that names no keyset, and adds the notes. A `Handover` is a service, a day, and for each note its amount, the note, its spend secret and its keyset. It carries spend secrets, so whoever holds the file holds the notes. **The type is sp-wire's**: `store::Handover` and `store::HandedNote` are re-exports of `sp_wire::esp::handover::{Handover, HandedNote}`, the type fsp-mint's `export-esp` writes, and the `receive` command reads the file with `Handover::read`, which refuses what is not a hand-over, a file with no notes and a note with a missing or empty keyset (naming the note). `receive_handover` takes a typed `Handover` that need not have come from a file (the wallet builds them too), so it keeps its own checks of the notes and the keyset.

**What was removed.** The wallet used to hand ESP to a service itself (`hand_over_esp`, the `hand-over` command), take it in (`receive`), and swap it at the ESP mint (the `transfer` command, with `cancel_transfer` and `mark_spent_in_transfer`). They were for passing ESP between two terminals before AIR existed. FSP issue now carries the hand-over over AIR, so they were removed with their tests (`tests/transfer_flow.rs` and the unit tests that used `hand_over_esp`). `receive` stays for `export-esp` only. The service's own swap (`build_transfer`, `finish_transfer`, `mint_info::send_transfer`, and the pending-transfer record that reserved the old notes) was removed last, with the tests that played the service against esp-mint: nothing in a wallet makes a transfer, so a library that every app embeds does not carry one.


`pick_exact` (the search for a set of whole notes that adds up exactly, depth-first with a budget of 100,000 steps) stays too: `fsp issue` uses it to choose the ESP notes of a hand-over, since a holder cannot split an ESP note.

### Redemption

```
fetch_redeem_fees(wallet, air) -> RedeemFees { fee_per_byte, max_request_bytes, max_memo_bytes }
build_redemption(service_secret, memo, fees, now_unix) -> Vec<RedeemBuild>
send_redeem(wallet, air, body) -> RedeemResponse            (or WalletError::RedeemRefused)
rebuild_redemption(id, service_secret, totals) -> RedeemBuild
finish_redemption(id, response) -> RedeemOutcome
cancel_redemption(id)
pending_redemptions() -> &[PendingRedemption]
```

This follows esp-mint's `POST /redeem` as it is built (see "Redemption" in the esp-mint README). Only the service redeems: the request names the service, every input is signed over the request digest with the note's own key, and the whole request is signed with the service's DID key. The wallet builds the mint's canonical binary encoding (`esp_mint::redeem::encode`) and sends it as `application/octet-stream`.

What goes in. `build_redemption` takes every free ESP note for the service whose key is `service_secret` and whose redeemable-after day has come on the wallet's clock (`now_unix / 86400 >= day`). Mixed days are allowed. Notes of other services, and notes not yet mature, are left alone. The memo says where the payout goes (for example `btc:ADDRESS`). It must not be empty or blank and must fit `max_memo_bytes`.

Size and fee. The size is exact: `120 + 187 per input + memo bytes + 82 per output` (decline and refund outputs alike), which is `sp_wire::esp::redeem::encoded_len`. The fee is `size × fee_per_byte`, with the rate taken from `GET /fees` (the `redeem` block, whose size constants the wallet checks against 120, 187 and 82). `RedeemBuild` and `RedeemOutcome` report `size_bytes`, `fee_per_byte` and `fee_esp`, and the command prints them before sending.

Outputs. The accepted value minus the fee comes back as decline outputs, held under each note's own service and day (the mint checks the total against what it owes and each day against what it accepted). The fee is taken from the service and day with the most value first, then the next largest, so small days keep their value. The mint does not fix where the fee comes from: it checks only the total and each day's cap. Amounts over `u64::MAX` are split into several outputs. The output count changes the size and so the fee, so the wallet repeats the sum until it settles. If the notes are worth less than the fee, or the fee would take all of them so that the mint would owe nothing, that request is not sent and the wallet says why (`not sent: ...`, printed by the command). Its notes stay free. When no request is left the result is `NotEnough` with the same reason. `plan_redemption` returns the built requests together with these reasons; `build_redemption` returns just the requests.

Splitting. If the request would be larger than `max_request_bytes` (from `/fees`, or lower with `--max-bytes`), the notes are split, oldest day first, into several requests that each fit, counting the worst case for outputs. Each part is its own request with its own fee and its own payout entry. A ceiling too small for even one note (a request for one note can need 10,803 bytes before the memo, with the most decline and refund outputs a service and day can have) is refused, and the message names the limit in force: `--max-bytes N` when the caller's own, lower ceiling is the one that applies, `the mint's ceiling of N bytes` when it is the mint's (a `--max-bytes` above the mint's changes nothing: `RedeemFees::ceiling`). `redeem` prints the summary first (`fee rate …; at most N bytes a request; N request(s)`, with `(--max-bytes)` after the bytes when the caller's ceiling is the one in force), then one `not sent: …` line for each part left out (`RedeemPlan::lines`), then each request.

Crash safety. Each request is stored in the wallet file by its request hash (`sp_wire::esp::redeem::request_hash`, also the mint's entry id) with its exact bytes, and its notes are reserved by that id before it is sent. The blinding factors for its decline and refund outputs are stored with it. After a lost reply or a fault, send the same bytes again: the mint keeps its answers by request hash, so nothing is burned or queued twice. `finish_redemption` can be given the same answer more than once.

Bad proofs. A note the mint rejects for a bad proof (in a reply or in a refusal's totals) stays in the wallet and in the balance, but its id is saved in the wallet file (`bad_proof`) and redemptions no longer pick it. `balance` prints `bad proof N note(s) worth X ESP`. `is_flagged_bad_proof(id)` checks the flag and `clear_bad_proof(id)` clears it.

The answer. Each note gets a decision: accepted, or rejected with a reason (`wrong_service`, `bad_proof`, `already_spent`, `immature`) and whether it was burned. `finish_redemption` removes burned notes, moves `already_spent` notes to the spent record, flags `bad_proof` notes, and frees the rest. Refund outputs the mint signed are unblinded into notes. With an owed amount the message is "payout queued" and the entry is open. When the fee takes everything the message is "nothing owed, fee taken", there is no entry, and the redemption ends.

Refused requests. A `400` or `413` is `WalletError::RedeemRefused { code, why, totals }`. For `refund_required` and `outputs_over_limit` the mint sends its `totals` (each note's decision and the accepted and rejected value by service and day). `rebuild_redemption` drops `already_spent` notes to the spent record, frees `wrong_service` notes, flags `bad_proof` notes (below), and builds a new request from the mint's figures: if the accepted notes cannot pay the fee, the genuine rejected ones (for example, immature on the mint's clock) pay the shortfall and the rest comes back as refund outputs. The old request is replaced. The command does this up to 4 times. Any other refusal frees the notes (`cancel_redemption`). `below_fee` means even all the genuine notes do not cover the fee.

Collecting. A queued redemption stays in the wallet with its notes gone. Sending the same request again returns the entry's state: `open` (nothing to do), `completed` (with the operator's payment reference; the redemption ends) or `declined` (the operator's reason and the mint's signatures on the stored decline outputs, which the wallet unblinds into notes under the original days; the redemption ends). `cancel_redemption` refuses a queued redemption.

### FSP

The decisions behind FSP (the eight answers, the crash ordering, rotation) are in the [fsp-mint DESIGN.md](../fsp-mint/DESIGN.md); this is the wallet's side.

- **Issue.** `build_fsp_issue(service, units, fee_per_byte)` takes the app's free ESP for that service (any days mixed: FSP ignores maturity), groups it by day, makes power-of-two FSP outputs worth the ESP less the fee, and stores the request as pending (notes reserved) before it is sent. `fsp issue` sends it to the service's FSP mint as an AIR call (kind 11, FSP issue).
- **Pay.** `build_fsp_spend(service, units, memo)` picks FSP notes on the current or previous keyset, adds change outputs on the current one, and stores the request. `fsp pay` sends it as an AIR call (kind 12, FSP spend). **A refusal that names spent notes.** If the mint answers `note_spent_elsewhere` with `spent` (the positions of the inputs it already has spent; fsp-mint names all of them), `settle_fsp` marks exactly those notes spent (they leave the balance, are listed by `balance` as "spent elsewhere" and are not picked again), frees the request's other notes and drops the request (`Wallet::mark_spent_in_fsp`). Before, the wallet read it as a plain refusal, freed every note, and the next `fsp pay` or sync picked the same spent note again. For `fsp pay` and `fsp issue` the error is `SpentElsewhere` and its text says what was done; for the automatic rollover the same marking is a line in the log (`rollover refused (…): N note(s) marked spent, M freed`) and the next rollover is built from the notes that are left. For an issue, the positions count the ESP notes across the groups in order. **A refusal that names a position the request does not have** (or names none) is a `Mint` error and marks nothing: the mint's answer cannot be used, so `settle_fsp` cancels the request and frees its notes as it does for a plain refusal, and the next connection builds a new one. Before, the wallet's own check (`Invalid`) came out through `?` with the request left pending, and it was sent again on every connection. That holds for a rollover, `fsp pay` and `fsp issue`. Not covered: a group of an issue that the Issuer refuses for a spent ESP note (`GroupResult::Refused`) still frees that group's notes; the restore sync is a later item.
- **Crash safety.** Every FSP request is stored with its request hash before it is sent. A crash, a lost reply, a signed "cannot answer now" (the `5xx` of the old routes, an ESP mint that does not answer fsp-mint included) or a `409` leaves it pending; the next connection sends the same request again and finishes from the mint's stored answer. A `400` frees the notes.
- **Automatic rollover.** On every connection to an FSP mint, and at startup for every FSP mint the wallet knows, `fsp_sync` reads the keys (AIR kind 2), finishes pending requests, marks notes on a keyset the mint no longer has as lost (kept in `lost_fsp`, shown by `balance`), and swaps every note on the previous keyset for the current one (`build_fsp_rollover`: a spend that pays 0). No prompt. A failure is logged and retried on the next connection. The swap is staggered: each wallet waits its own delay after the rotation, at least a second and at most 0.5% of the period and never more than 72 hours (drawn at random once and kept only until the swap is done; see "Swap times are not kept" below; using the mint's clock from its rotation call, kind 4), so all wallets do not swap at once. *Why automatic:* a note left on the previous set through the next rotation is lost, and a holder should not have to know about rotation.
- **Lost FSP.** FSP that sat in a wallet that never connected for a full cycle (one to two periods, one to two years by default) cannot be used; the mint has deleted its keyset and its spent list.
- **The window.** `fsp_rotation` makes the rotation call (kind 4); `fsp-window` prints it.
- **ESP schedule.** `esp_schedule(service, by)` reads the wallet's own ESP notes (no mint call) and gives what is mature now, what is mature by a date, and a by-month breakdown. It is for the service, which holds the ESP it took in for FSP until it matures.

### Rotation of PSP and ESP

psp-mint and esp-mint rotate the same way (activation 8760 hours after the first issue, period 87600 hours, two key sets and two spent lists). At startup, when the wallet holds that kind of note (and `air.server` and `air.host` are set, else it prints a note and skips), `mint_info::rotation_sync` reads the mint's rotation window over AIR, finishes pending rollovers, marks notes beyond the window as lost, and after this wallet's staggered time swaps previous-set notes with a rollover (batches of up to 1000 notes; ESP per service and day, keeping both). A failure is logged and retried at the next start. - **Keysets are recorded and named.** The wallet records the keyset of every PSP and ESP note: from the keys a claim was unblinded with, or from the mint's reply to a rollover or hand-over swap. Every PSP request names them (`input_keysets` and `keyset` on `/rollover`, `psp_input_keysets` on the ESP exchange), and the outputs of a swap name the PSP's current keyset, read fresh from the rotation window at each connection (the cached live keysets are replaced every time, so they cannot go stale). A token carries each note's keyset.
- **ESP keysets.** ESP notes are keyset-addressed too. The wallet reads the ESP mint's live keysets (`GET /keysets`, and `/rotation` on each rotation sync) before an exchange or redemption, names the current one for new outputs (exchange `keyset`, the redemption's output keyset) and each note's recorded keyset for its inputs (rollover `input_keysets`, one keyset per redemption input, and `keyset` on each FSP issue note and hand-over note). New ESP notes record the keyset the mint's reply names (exchange and rollover replies, and each decline or refund signature), which can differ from the one asked for (a queued decline signed after that set retired), and they are unblinded with that reply's keys. A PSP claim is unblinded with the keys of the keyset the PSP's record names, taken from the keysets inside that record (checked against the keyset id), never the current set by assumption. A redemption without a known current ESP keyset is refused locally ("connect to the mint first").
- **The keyset is remembered for each pending request.** A pending exchange, redemption or rollover keeps the keyset its outputs name. Mints sign with whichever live keyset (current or previous) a request names, so a request built before a rotation is sent as it is and the reply names the keyset that signed. If the named keyset has been deleted since (two rotations), the mint refuses `keyset_retired` before burning anything, the wallet frees the notes, and the request is built again from a fresh read of the keysets. There is no re-blinding step.
- **No keyset guessing.** Every note the wallet stores records its keyset (from the reply that signed it, the PSP claim, or the hand-over or handoff that brought it). A note without one is refused with "note X has no recorded keyset, so it cannot be spent"; it is not picked for rollovers. A hand-over note without a keyset is refused (a handoff cannot hold one: its format requires a key set for every note), and a mint reply that names no keyset is not stored. Redemption sizes are now `119 + 186 × notes + memo + 81 × outputs` (format version 2); exchange `48 + 146 × notes + 41 × outputs`, transfer `120 + 146 × notes + 41 × outputs`.
- **A note claimed on the current set after a rotation is not rolled over.** The rollover picks notes by their recorded keyset (any but the current set); a note with no recorded keyset is never picked.
- **Expired notes are written off with a message.** A note whose recorded keyset is neither current nor previous was retired: it is moved to `lost` (not in the balance), and the sync says "N note(s) expired: their key set was retired at a rotation before they were rolled over". A PSP record carries the keys of the set that signed it, so it claims whenever it is picked up, even after that set retired; the notes it gives are on that set and are written off like any other if they are not rolled over in time. A mint's `unknown_keyset` answer means junk or the wrong mint, not expiry.

- **Swap times are not kept (privacy).** Each rotation's swap time is a random delay (at most 0.5% of the period, capped at 72 hours, from the mint's clock) drawn once and stored in `swap_schedule`, for FSP, PSP and ESP alike. It is deleted in the same atomic write that records the new notes when the rotation's last batch completes, and the whole entry is dropped when the old set retires. No history is kept, and the logs never print a swap time.

### Handing PSP to another wallet

For a developer that sells PSP to its users by in-app purchase, with this wallet inside the app. There is one way to do it, the PSP handoff (next section). The older `send-psp` token (`send.rs`, `psp1`, `receive-psp`, `sent`) was removed in 0.5.0: it did the same job with a bearer token that was not encrypted. What was worth keeping moved into the handoff: the reclaim and the check. *Why always a swap at the mint:* a developer who double-spends only hurts its own users, but the swap costs almost nothing and protects against accidents such as a wallet restored from an old backup or a bug that reuses notes. ESP and FSP still always go through their mints.

- **Reclaim and check (the sender).** An outgoing PSP handoff keeps the notes and the PSP mint (`OutgoingHandoff { notes, mint, reclaim, spent_elsewhere }`). `mint_info::check_handoff` asks the PSP's check-state (over AIR) for the nonces: none spent leaves it `Pending` (`Standing::Pending`); all spent ends it as `Done` and drops the notes (`Standing::Received`); some spent drops those notes, counts them in `spent_elsewhere` and leaves the rest reclaimable (`Standing::Partly`). `mint_info::reclaim_handoff` stores a swap of what is left back to this wallet (`Wallet::begin_reclaim`, tag `reclaim|<id>`, the handoff's `reclaim` field points at it) and sends it. The mint takes the first swap that reaches it, so the record at the mint decides: if the receiver was first, the mint refuses (`note_spent_elsewhere`), the stored swap is dropped, the handoff stays pending and the next check finds the notes spent; if the sender was first, the handoff ends as `Reclaimed` and the fresh notes are in the balance. The stored swap's outcome and the handoff's state change **in the same write** (`finish_rollover`, `cancel_rollover` and `mark_spent_in_rollover` call `handoff::settle_reclaim` inside their own `update`), so a crash cannot leave a finished reclaim recorded as pending. A repeat of the request gets the mint's stored answer by request hash.
- **No lock on unswapped notes (the receiver).** Before 0.5.0 a received PSP handoff was held only inside its stored swap, in no balance and unspendable, because `send-psp` could pass such notes on without swapping them. With `send-psp` gone the lock bought nothing: a note spent at the mint is burned just like a swapped one, so whichever of the swap and the spend reaches the mint first wins and the other is told. Now the import adds the notes to `notes` (with their key sets recorded) and stores the swap beside them, unreserved. The swap is sent first thing whenever the mint answers: `http::complete_import` on import, then `rotation_sync`, which sends stored swaps before anything else, at startup and on every connection. `Balance::psp` counts them; `Balance::unswapped_psp` says how much of it is still waiting.
- **Keeping the stored swap true.** The swap names its inputs, so a note spent here since (handed on, exchanged) would make the mint refuse the whole request. `send_rollover` first calls `Wallet::live_swap`, which replaces the stored swap by one for the notes still held and free (or drops it if none is). `prepare_rollover` leaves notes that are inputs of a stored received swap out of the ordinary rollover. When the mint does refuse with `note_spent_elsewhere` (the sender reclaimed first, or a copy was received first), `Wallet::swap_found_spent` moves the named notes to the `spent` record, so they leave the balance (they were never this wallet's), and the swap is rebuilt for the rest and sent again; the mint reports one spent input per refusal, so this repeats until the rest is swapped. Any other refusal drops the stored swap and leaves the notes in the balance as they are.
- **Old records are not read.** The `sent` list of a wallet file from 0.4.0 or earlier is not read (the wallet used to turn each token into an `OutgoingHandoff`; that reader, `legacy.rs`, was removed), and a file that holds a combined handoff or a purchase without its one-off reply key does not open. Reclaim or settle such records with the 0.5.0 build first. *Why:* a reader kept only for old files is code that every app embeds and no real use of the wallet exercises.

### Handoff, merge and the service ID

Three pieces that let value and identity move between wallets without the AIR (`src/handoff.rs`, `src/merge.rs`, `src/store.rs`). *Why:* an unfunded wallet cannot pay to read from the AIR, so a new device or user needs its first notes, and its identity, from another device or from an app. And a wallet restored from storage may be older than the one on the device.

**Handoff: exactly two kinds.** (`src/handoff.rs`.) v0.4.0 had one combined handoff (PSP, FSP and an optional DID key, swap optional), which let you build combinations that make no sense: a PSP handoff with a DID key, unencrypted, or unswapped; an FSP handoff swapped. That was a bug, so the combined kind is gone and there are two, each with its own types, string prefix and import:

- **PSP handoff** (`SPHP2:`), a developer to a user. `PspPayload { mint, notes }` has no field for a DID key or FSP. `export_psp_handoff(ids, psp, recipient)` takes the PSP's DID (the handoff names the PSP by it in lowercase hex), needs the recipient's DID public key and seals the body to it with `sp_wire::seal::encrypt` (AIR's `PublicKey::encrypt`; sp-wire's module is the one place that wraps it, so nothing new was written and the format of what is sealed is the mint payload's). `import_psp_handoff(text, key, psp, from)` opens it with the DID secret key, refuses a handoff that does not name this wallet's PSP `psp` by its DID in lowercase hex (a URL, a name, another DID or capitals are `Invalid`, and nothing is added), adds the notes to `notes` and **always** stores a PSP swap (`POST /rollover`) in the same write as the import record; there is no parameter to skip it. The swap is stored under the tag `handoff|<id>|<n>` and sent at once by `http::complete_import`; if the mint cannot be reached it stays in `pending_rollovers`, `Balance::unswapped_psp` (and `balance`) shows the units still waiting, and `rotation_sync` sends it on every connection to the mint and at every start (see "Handing PSP to another wallet" for why the notes are not locked meanwhile, and what happens when the mint refuses).
- **FSP handoff** (`SPHF2:`), a user's old device to the new one. `FspPayload { groups, did_key }` has a non-optional DID key and at least one group; `export_fsp_handoff(ids, did_key)` takes FSP notes only. It is not encrypted, because it carries the key it would be encrypted to. `import_fsp_handoff(text, from)` adds the notes as they are and returns the DID key for the caller to keep (the wallet does not); there is no swap, since both devices are one owner's. After the AIR fetch (not built) `merge FILE` unites the small wallet with the fetched one.

- **The SPI's own revenue (`receive-psp FILE`).** Not a third handoff kind: psp-mint reissues the PSP a spend paid to the SPI (unless burning is on) and writes it to `revenue/<request hash>.json` as a `sp_wire::psp::PspHandover`, in the clear, because the file never leaves the SPI's machine and its folder is mode 0750. `Wallet::import_psp_file` turns it into the one-group PSP import a sealed handoff makes (the group names the wallet's PSP by its DID, `air.psp_did`), so the same checks (the secrets, the key sets, notes already held) and the same swap at the PSP apply, and the notes are the wallet's alone once the swap goes through. The import's id is the first 16 bytes of SHA-256 of the file, so the file taken in twice is the same import and is refused, and a copy of the notes in another encoding is refused by the notes-already-held check. The checks that need no wallet (`check_psp_file`) run before the startup steps use the network.

Why the prefixes differ (`SPHP2:`, `SPHF2:`): the kind decides what is checked and how it is opened, so it must be known before any parsing, and a string of one kind can never parse as the other (the two bodies also start with a kind byte, 0 and 1, and a PSP body is refused if anything follows its notes). `kind_of(text)` tells a caller which key a string needs before it imports. The old `SPH1:` is refused with a message naming the new kinds (keeping it was not trivial: its meaning was the thing that was wrong). Old `handoffs_out` and `handoffs_in` records read as kind `combined` and are kept.

- **Bearer secret.** Both strings hold every note's spend key; the FSP one also the DID key. `PSP_WARNING` and `FSP_WARNING` are printed on standard error by every export and every import. The README and the module docs say it too.
- **Versioned, checked, bounded.** A version byte (1), a 4-byte SHA-256 check (of the sealed bytes for PSP), at most 1000 notes, every amount a power of two, and every spend secret must match its note's nonce. A damaged payload, another version or kind, a forged secret or a key set that is retired is refused with a message before anything is added. A note's signature can only be checked by the mint, so a note is known good only once it is swapped or spent (the command line then reads the FSP mints' keys, which moves notes on a retired set to the lost record).
- **Validated against what the wallet knows.** The key sets of a mint whose live sets the wallet has seen must still contain the note's set; for FSP the service and its mint are looked up. What the wallet has not seen cannot be checked, and the import says so in its warnings.
- **The id** is the first 16 bytes of SHA-256 of the unsealed body, so the sender and the receiver both have it, and it does not change with the seal's fresh key. **Double import:** refused by the id and by note: a note already held, or one that was held and has left (spent, handed off, lost), is never added again. A wallet also refuses to import a handoff it made itself.
- **Source.** Each imported note's id is listed in `handoffs_in` with the handoff id, its kind and the sender's name if given.
- **Cancel.** `cancel_handoff` puts the notes back and is local only; it is refused while a reclaim is stored (that one may already have reached the mint). For a PSP handoff the receiver swaps at once, so after a cancel the first of the two to swap or spend wins and the other learns from the mint: use `handoff reclaim` instead, which lets the mint decide before the notes come back. For an FSP handoff the receiver holds the same secrets until one of them spends, and the mint has no record of who holds an FSP note, so cancel is all there is. `finish_handoff` drops the notes once the sender knows it was claimed.
- **`send-psp` is gone.** The PSP handoff replaced it (above, "Handing PSP to another wallet").

**Reconcile.** `merge(local, stored)` (crate-private: apps go through `merge_from` or `merge_file`, which check the network) unites a wallet retrieved from storage with the local one, in either direction and any number of times (the result is the same). `Wallet::merge_from` writes it atomically, and writes nothing if nothing changed. It refuses a copy of another network (`Invalid`, naming both networks, nothing written), and `merge_file` also refuses a file that records no network, as `open` does; `merge` itself, a pure function of two `WalletData` that apps cannot call, does not look at the network and keeps the local one. The wallet file has a `version` counter, up by one on every write, and the merge keeps the larger. Rules:

- **Notes are united by identity** (the nonce). A note that is gone in either copy stays gone: it is in `spent`, `lost`, `lost_fsp`, a handover or a pending handoff, or the ledger below says it left. A done or reclaimed handoff wins over a pending copy of it. A note held in only one copy is added if it is not gone, which is how a new device receives the starter notes of the old one.
- **The ledger.** A tombstone set cannot say that a note was cancelled back into the wallet, so the file counts departures and returns: `departed[id]` goes up each time a note leaves `notes` and `returned[id]` is set equal to it when the note comes back. A note is gone when `departed` is larger than `returned`. The counters are kept by `update` (`track(before, after)`), so no code path needs to remember them; the merge takes the larger of each. Cost: about 70 bytes of file for each note that ever left.
- **Requests.** Pending purchases, exchanges, redemptions, FSP requests and rollovers are united by request id without duplicates. The `finished` set lists request ids that ended, so a stale copy cannot bring a finished request back, and a note reserved by a request is reserved by it in the result.
- **Maps** (key sets, epochs, the live key sets, FSP mints, swap schedule) are united with the local entry winning on a conflict.
- The merge never adds a note the ledger says left, never drops a note both copies hold, and never turns a spent note back into a held one.

**The service ID on FSP notes.** An FSP note's service is stored in its `terms.service` (with day 0), as for ESP, and is not part of what the mint signs: no wire change. `StoredNote::fsp_service()` reads it; `balance()` groups FSP by service (`Balance::fsp_by_service`) and spending, the rollover and the handoff work by service. fsp-mint's keys and mint info already report the service, and the wallet fills `terms` from them for notes that came from a rollover or a reply. A note whose service is not known is shown as `unknown` in `balance`, with a hint, and is not spent until it is known. Nothing is guessed.

### Settings and the storage policy

The wallet's first settings with a file (`src/config.rs`, the same shape as the mints': `SPECS`, an unknown key or a bad value refused with every problem listed, defaults then file then environment). `config.toml` sits beside the wallet file, or is named by `--config` or `$ECASH_CONFIG`; `ecash-wallet config` prints the values in use and where each came from.

The settings are the **storage policy**: `storage.wallet` and `storage.app`, each an ordered list of service IDs. `storage.wallet` is the AIR services that back up the wallet state and nothing else (index 0 the preferred service for the copy the wallet should always keep on the AIR, the rest further backups, in order; the local file stays the primary ledger); `storage.app` is where the app's own data is kept. The parser and the checks are `sp_wire::storage`, shared with the three mints (`storage.mint_state`), so a list means the same in all four: 66-hex AIR DIDs (the 32-byte x-only form is refused), at most 8, no duplicates, no empty entry; one entry is valid (one service and the local copy); empty means local only. Two backup services are plenty.

*Why wallet backup and top-up are separate settings.* Where the wallet's state is backed up and which service the wallet pays FSP fees to are different questions with different answers. A backup list is ordered by preference and wants a few services for redundancy; the service FSP is paid to is one service, chosen for the money, and an accident of the notes the wallet holds (a wallet that holds FSP for three services) must not decide it. Tying the two together, as the first version did (the primary of `storage.wallet` was the default `--service`), made a backup choice into a payment choice. So `storage.wallet` is the wallet-backup list only, and the `fsp` commands always take `--service` and refuse without it. A separate top-up setting is planned and not built; its name is open.

Config and validation only: nothing reads or writes the AIR. The wallet file is still the local file, with its `version` counter and `merge` for the day a copy comes back from storage. What the storage must provide is listed in the mints' DESIGN.md files ("Storage policy"): the wallet file is the one that carries a version and is merged (requirement 5 there).

**An owed PSP credit is shown as pending.** When a purchase was overpaid, the PSP's record says how many USD cents it owes, and the wallet keeps the purchase's key (`open_replies`) until the PSP's window closes. `balance` prints the sum under the PSP total, as `10 PSP (1.00 USD) (pending)` and the rest of the line (`Wallet::pending_psp_credit(now)` and `PspCredit`, for apps). The credit is not in the `psp` total: the wallet holds no note for it until it is claimed. The rate is the protocol's own and is fixed (10 PSP to the dollar, `sp_wire::units`), so a cent is a tenth of a PSP and the wallet always knows it. The line shows the units the claim will issue (the rules' `due_units`, after the PSP's rounding and fees) and the exact cents, for example `9 PSP (0.94 USD) (pending)`; the wallet never rounds by itself. It drops once the claim is answered, and does not return after a merge. A purchase whose window has closed (`open_until` is `now` or earlier) is left out, as `close_expired` would delete it.

### Reconciliation (AIR kind 15, `PSP_RECONCILE`)

The PSP's first record carries `rules` (`sp_wire::air_request::delivery::ReconcileRules`) for a held payment, a rejected purchase with a readable payload, and a credit: `send` (`corrected_request` or `credit_claim`), `due_units`, `open_until`, `max_attempts`. The wallet stores them with the open purchase (`OpenPurchase.rules`) or the kept key (`OpenReply.rules`). They are required: a held or rejected record with no rules, and a credit with none, is a mint error and nothing is stored. The wallet never works from the PSP's current settings, only from these.

`Wallet::open_reconciliations(now)` lists the payments to settle and where each stands (`ReconcileStatus`: `Due`, `Sent`, `NothingDue`, `Lost`). `Wallet::build_reconcile(id, keysets, now)` builds the request: outputs that are fresh blinded powers of two, each at most the PSP's largest note, adding up to `due_units` exactly, with distinct blind nonces (1 to `MAX_ROLLOVER_NOTES`), on the PSP's current keyset, signed with BIP340 by the purchase's reply key over `ReconcileRequest::digest`. `psp::check_reconcile` checks all of it (kind 15, `now` before `open_until`, the reply DID and purchase id, the signature, a live keyset whose keys hash to its id, the output count, denominations, distinct nonces and the exact total) before anything is saved; a request that fails is a wallet bug, refused with nothing saved and nothing sent. The request's bytes and hash, its blinding factors and the `PendingAirRequest` that carries it (kind 15, `r` the reply key) are saved with the payment in one write, before the first AIR write (`air::call_with_key`). `mint_info::psp_reconcile(wallet, air)` does the whole step and is called at every wallet start, right after the PSP pickup, and by `claim-psp`; there is no command of its own.

A request is never changed once saved. The PSP answers an accepted request only, so an unanswered one is sent again as the identical bytes, once per start (`air.attempts` tries), until `open_until`, plus one final identical resend at the close (below); an identical resend of an accepted request gets the stored answer, so a lost reply is harmless. The one second request exists for the keyset-rotation race: after an ask ends with no reply, the wallet reads the PSP's keysets again, and if the saved request's keyset is neither current nor previous it builds one more on the current keyset. Requests built never exceed `min(rules.max_attempts, 2)`, counted in the wallet file. After those have gone unanswered, `Reconciled::NotAccepted` tells the user once that the PSP did not accept the request and the funds are lost at `open_until`.

**The final resend at the close.** The PSP answers an identical resend of a request it took even after `open_until`, and never forfeits a payment with a pending record, so deleting the payment without asking once more could lose funds that were settled. `mint_info::psp_close_expired(wallet, air, now)` therefore sends, for each payment whose `open_until` is `now` or earlier and that has a saved request, that request once more: the saved bytes, identical, with the usual `air.attempts` tries; no request is built, even when the keyset left the live set, and nothing loops. An answer is checked and applied by `apply_reconcile` and the payment is settled (no loss is reported); with no answer, a refusal or a bad answer the payment is deleted and reported lost. **A payment whose final send could not be made is not deleted:** when the AIR settings are missing, or the call fails (the AIR server cannot be reached, which stops the sends), the payment and every later expired payment that was not tried are kept with their key and saved request (`Closed::kept`), and the close is tried again at the next start; deleting them would lose payments the PSP may have settled already. A payment with no saved request, and a payment sealed to another PSP than `air.psp_did`, are deleted with nothing sent. Only then does it call `Wallet::close_expired_keeping` (`Wallet::close_expired` with the kept payments left alone), which stays free of network use. The command line does this at every start and in `claim-psp`, before the startup reconcile.

`Wallet::apply_reconcile(id, response)` checks the answer before it stores anything (the keyset's keys, listed in the answer, hash to its id, one signature per output in the request's order, `issued_units == rules.due_units`); the answer's keyset need not be the request's: psp-mint signs a request it had already taken (a pending record) with its current keyset when the request's keyset was deleted, and the reply names the signer, so the notes take the signing keyset; a failure is a mint error, nothing is stored and the key is kept. Then, in one write, it unblinds and stores the notes, records the keyset, removes the purchase or `OpenReply`, its key, the saved request and the `PendingAirRequest`, and adds the id to `reconciled`. Applying an answer to a payment that is gone changes nothing. When `due_units` is 0 (the PSP's fees take the whole amount) nothing is built or sent, and `psp_nothing_due` tells the user once.

`merge` carries a saved request with its payment: a copy that has the payment and no request takes the other's; where both have one, the local copy's is kept; `told_lost` is or-ed; and a payment in either copy's `reconciled` is in neither result, so a settled credit and its pending line never come back.

**Minimum purchase.** `psp.min_purchase` (`ECASH_PSP_MIN_PURCHASE`, PSP units, 50 by default, 1 or more) is the wallet refusing to build a payload below it: `build_psp_payload` and `buy-psp` refuse, before any network use, with a message that names the setting. Nothing in the PSP changes. The PSP's fees come out of what a payment buys, so a small purchase can be eaten whole; 100 PSP is a realistic purchase, and lowering the setting is not advised. `buy-psp` prints `psp::ONE_TIME_USE` with the purchase id: the PSP settles a payload once, and a second payment carrying it buys nothing.

**Credit rounding.** The PSP issues a credit in whole units (10 cents each) and rounds by its `reconciliation.round_up_from` (9 cents by default): a remainder of that many cents or more rounds up, a smaller one is kept by the PSP. A credit of 8 cents or less is therefore 0 units and is lost. The wallet claims exactly `rules.due_units` and never rounds by itself; the pending line shows both, for example `9 PSP (0.94 USD) (pending)`.

### The PSP's calls over AIR (mint info, keys, keysets, rotation, rollover, check-state)

`mint_info` is the one place the PSP's calls are made (`verify_psp` for mint info, `psp_keys`, `psp_keysets`, `psp_window` and the calls built on them for the reads, `psp_post` for the two POSTs, and `psp_pickup`, which reads the delivery records), **over AIR only**: it takes the run's `AirSettings` and every call first asks `AirSettings::require`, so without `air.server` and `air.host` it fails with an error that names the missing setting and sends nothing. The DID is the built-in SPI DID or `air.psp_did`. The command line calls it wherever it calls the PSP (`buy-psp --sync`, `claim-psp`, `handoff export-psp`, `handoff reclaim`, and the startup rotation check); the FSP calls are in the same module, below. The PSP's `/melt`, `/burns` and `/audit` are between the mints and the operator and are not the wallet's. The ESP's calls are the next section. The design, the wire and the reasons are `air-sandbox/REQUEST-DESIGN.md` in sandbox-mint and `sp_wire::air_request`; what is specific to the wallet:

- **Where the code is.** `air.rs` is the wallet's part around `sp_wire::air_request::ask::ask` (`call` returns the verified reply of any kind, `fetch` reads its body as the type the route used to return, `verify_mint` is `call` plus the mint-info check); `config.rs` holds the `[air]` settings; `store.rs` holds `PendingAirRequest` (with its `kind`, which defaults to mint info so an old file loads as it was) and `WalletData::air_requests`. The binary only keeps the `[air]` settings of the run and remembers the first answer for the run. The `air` cargo feature is gone: `sp-wire`'s `air-client` is always built in, so a build needs the `air_server` patch described in the README.
- **Why server and host go together, and the DID defaults.** The wallet needs the SPI's DID (where the mailbox is and whose signature to check), the AIR server's name (so only that server is accepted) and its host. The DID is built in, because the wallet ships knowing the SPI it talks to and `air.psp_did` is an override (the ESP has its own, below); the server and host are configuration until upstream item 4 resolves them from the DID. Server without host (or the reverse) is refused when the settings load, and so is `air.psp_did` without both (it would be ignored), so a half-written file is caught when the settings load. There is no "AIR off" any more: without the server and host the PSP's and the ESP's calls fail with the error that names them.
- **The built-in DID is a PLACEHOLDER.** `config::BUILTIN_SPI_DID` is a point with no known private key, derived in the open (the x is `sha256("ecash-wallet placeholder SPI DID v0" || [3])`, the first counter that lands on the curve), not the generator (whose key is 1, so anyone could read and sign for it). Nothing sealed to it can be opened and no reply can verify, so using it by mistake fails safe. It must also fail loud: `AirSettings::placeholder_warning` is non-empty whenever AIR is set and it is in use, the command line prints it at every start and in `config`, and the errors that name the PSP's DID say "PLACEHOLDER". The real DID replaces the constant at the first SPI deploy (OPERATIONS.md step 0).
- **One kept request per PSP and kind.** The kept request is looked up by PSP and kind, so a kept mint-info request is never taken for a keys request, and the four calls do not wait for each other. All four have the same retry, end and late-reply rules.
- **Rollover and check-state: a `Post` source.** `send_rollover`, `check_handoff_with` (and so `reclaim_handoff`), `complete_import_with` and `rotation_sync_with` take a `Post` (a function of the wallet, the route and the request JSON that returns the mint's answer as JSON or the wallet's error), the way the window is a `WindowSource`; the PSP passes `mint_info::psp_post` and the ESP `mint_info::esp_post`. The code that reads a `Refused`, a `SpentElsewhere` or a `Mint` error is shared. The wallet's refusal mapping lives in `error::mint_refusal`.
- **The kept request of a call with a body is found by its body.** `PendingAirRequest.body_hash` is the SHA-256 of the request body (empty for reads). The body is not kept in the file: it is rebuilt byte for byte from the stored pending rollover (`serde_json::to_vec` of the same `Value`), so the hash is the same on the next run. Two rollovers waiting for an unreachable PSP are two kept requests; a changed rollover (a live swap that dropped notes) is a new one; an orphan is dropped after 30 days (`store::AIR_REQUEST_KEEP_SECS`). A resent request, with the same body, gets the same answer from the mint, so dropping or repeating a kept request never applies a rollover twice.
- **Refusals.** A signed `STATUS_REFUSED` reply is turned into the error the HTTP `400` becomes (`Refused("code: why")`, or `SpentElsewhere`); `request_too_large` is a `Mint` error, as the `413` is, so nothing is cancelled for it; a signed "cannot answer now" is a `Mint` error ("could not answer rollover now"), and the rollover stays stored for the next connection. The wallet cannot tell a refusal from a lost reply except by the reply, so it never cancels on silence.
- **The logic is shared between the PSP and the ESP.** The choices are written once and take the way of reading as a parameter: `psp::claim_keys_with` (which keyset's keys unblind a settlement, and the "no longer live" refusal), `mint_info::rotation_sync_with` and `reclaim_handoff_with` (a window source), and `rotate::Window::from(RotationResponse)`. The FSP's rotation window is read over AIR like theirs (`mint_info::fsp_window`).
- **No caching.** Every call fetches fresh; only the first mint-info answer is kept for a run (the binary's `PSP_CHECKED`), because a dead PSP costs 3 x 30 s over AIR. A dead PSP fails that check first, so the keys calls that follow it are not tried.
- **What the signed body adds.** The keys, the keysets and the window are read from a reply the PSP signed with its DID key, so a wallet that is told which PSP to trust (`air.psp_did`) cannot be given other keys by anything between it and the PSP. A signed body that is not the type asked for is refused as the PSP's own fault, and a signed "cannot answer now" is `WalletError::Mint` ("could not answer keys now"), which the existing code treats as retry-safe.
- **The request lives in the wallet file.** `request_id` and the one-off key `r` are saved (a normal atomic write, `version` goes up) before the first write to the mailbox and after each one. They are all that is needed to read the reply, so a lost reply is recovered by reading the reply cell first; only if it is empty is a request written. The record is local: `merge` keeps this copy's, and a record for a PSP that is no longer configured stays until that PSP is configured again and the request ends (it holds no money).
- **When a request ends.** It is removed when the reply verifies, and when a reply arrives that fails a check (the cell is write-once, so the request can never be answered differently). It is not removed when the PSP did not answer: that call returns the error and the next call resumes the same request.
- **A late reply is not current.** A resumed request whose reply is older than `air.max_skew_secs` is dropped and one new request is made in the same call: each of these calls is how the PSP is now (and an old reply of keys is how retired keys would come back).
- **Errors keep their kinds.** A reply with another network is `WalletError::Invalid` with the same words for every mint; another wire version is `WalletError::Wire`; no answer, a refused reply and a server that cannot be reached are `WalletError::Mint`, which the existing code treats as "retry is safe".
- **Blocking.** The AIR client is async; the call runs it on a runtime built for the call on a thread of its own (`sp_wire::air_request::client::block_on_new_runtime`), so it works whether or not the caller is inside a runtime.
- **HTTP is gone for the PSP.** The wallet's HTTP functions for the PSP's mint info, keys, keysets, rotation, rollover and check-state, and their `!air.is_configured()` branches, were removed in 0.6.0 (see the changelog); the `NotBuilt` error went with the `air` feature.

### The ESP's calls over AIR (mint info, keysets, rotation, fees, rollover, exchange, redeem)

`mint_info` makes the ESP's calls as it does the PSP's, over AIR only: `verify_esp`, `sync_esp_keysets`, `sync_esp_limits`, `fetch_redeem_fees`, `esp_window`, `esp_post` (the rollover), `send_exchange` and `send_redeem`, and `rotation_sync` for either mint. The wire, the kinds and the decisions are REQUEST-DESIGN.md section 16 (sandbox-mint) and `sp_wire::air_request`; what is specific to the wallet:

- **`Party`.** `config::Party` (`Psp`, `Esp`, `Fsp(service)`) says which mint a call is for: the DID (`AirSettings::psp_did`, `esp_did`), the setting that overrides it, the placeholder, and the words of messages. It lives in `config.rs`, not `air.rs`, `air::call`, `call_with_body`, `answer`, `post`, `fetch`, `fetch_text` and `verify_mint` take it. Kept requests (`PendingAirRequest`) already hold the mint's hex and the kind and body hash, so the PSP's and the ESP's never collide.
- **Two DIDs.** `BUILTIN_ESP_DID` is a PLACEHOLDER derived in the open like `BUILTIN_SPI_DID` (a different counter and domain string, so the two differ; a test checks that), and `air.esp_did` overrides it. `AirSettings::placeholder_warnings` lists the warning for each placeholder in use; the command line prints them at every start and in `config`, and an unreachable mint's error names its own DID's setting. `air.esp_did` without server and host is refused when the settings load, as `air.psp_did` is.
- **The answer is read with the route's readers.** `esp_replies.rs` holds how the fees reply and the ESP's refusals are read (`exchange_refusal`, `redeem_refusal`), so a refusal becomes the `WalletError` it always was. `air::send_esp` takes the body, the refusal reader and the statuses that mean a refusal (exchange: `400`; redeem: `400` and `413`). A signed refusal whose JSON carries `"http_status": N` (N is not 400) is not a refusal of the request but a status the mint's route returned (`409 in_progress`, `413` on exchange, `404` rotation): it is `WalletError::Mint` with the status, so a pending exchange is **not** cancelled and its notes are not freed. Treating it as `Refused` would cancel an exchange the ESP may still be answering.
- **The exchange needs the output keyset.** `sync_esp_keysets` sets `esp_output_keyset()`; the command line calls it (and `sync_esp_limits`) before `build_exchange`. The PSP's input keysets come from the wallet's own `keysets` map, as before.
- **Resends.** The exchange and redeem requests are kept by body hash. The pending exchange or redemption already stores the request body, so the next run resends the same bytes, and the ESP's answer by request hash makes that safe. An "unavailable" reply (a `5xx`) for these says that the outcome may be unknown (not "nothing was sent"), and to send the same request again.
- **Rollover.** `rotation_sync_with(wallet, kind, base, WindowSource, Post)` is the one sync for PSP and ESP; for the ESP the window is `esp_window` and the post is `esp_post`, both of `mint_info`. `error::mint_refusal(body, code, why)` is the one mapping of a rollover refusal.
- **Same behaviour as before.** The errors, the pending records and the resend rules are those the HTTP calls had; only the way of carrying the request changed.
- **No HTTP is left for the ESP** in the wallet either (removed in 0.6.0). The ESP's `/audit` and `/health` are the operator's and the SPI's own, local to the ESP's machine.

### The FSP mints' calls over AIR (mint info, keys, rotation, fees, FSP issue, FSP spend)

`mint_info` makes a service's FSP-mint calls as it does the PSP's and the ESP's, over AIR only: `verify_fsp`, `fsp_keys`, `fsp_rotation`, `fsp_window`, `fsp_fees`, `send_fsp_issue`, `send_fsp_spend`, `settle_fsp` and `fsp_sync`. The wire, the two new kinds (11 FSP issue, 12 FSP spend) and the status mapping are REQUEST-DESIGN.md section 17 (sandbox-mint) and `sp_wire::air_request`; what is specific to the wallet:

- **`Party::Fsp(service)`.** The mint is the service's own, so the DID is the service's, and the AIR server and host are the ones in the service's **`air.fsp` entry** (`<service DID>@<AIR server key>@<host>`, `FspAir`, `AirSettings::fsp_for`). The PSP and the ESP share `air.server` and `air.host`; an FSP mint cannot, because every service runs its own, so the setting is a list with one entry per service. It is checked like `air.server` and `air.host` (each part, no duplicate services) and has an environment form (`ECASH_AIR_FSP`, comma-separated). A call for a service with no entry fails before anything is written, with an error that names `air.fsp`, the variable and the service.
- **Why a setting and not a lookup.** Finding a service's AIR server from its DID is upstream item 4 and is not built, so the entry is configuration. It is marked in the code and the docs as **to be replaced by DID resolution**; when that exists, `Party::address` is the one place that changes.
- **The kept mint records are keyed by the service**, in hex, where they were keyed by URL. The swap schedule's key is `<kind>|<record>|<keyset>` with the service hex as the record. The PSP's and the ESP's records (their live keysets, their swap times, the mint a handoff names) are keyed by their DIDs (`air.psp_did`, `air.esp_did`, `fsp::record_of`) as an FSP mint's are; the `PSP_RECORD` and `ESP_RECORD` labels are gone. A record kept under an old label is not read and not migrated.
- **A handoff of FSP names the mint by its service.** The group's `mint` field is part of the string's format and is never empty, so it carries the service's DID in hex and nothing else (the reader refuses a handoff that names anything else there, a URL included, with `Invalid`); the importer reaches the mint through its own `air.fsp` entry. The check that warned when the receiver's mint URL differed from the sender's is gone with the URL.
- **A handoff of PSP names the PSP the same way.** Its `mint` field is the PSP's DID in lowercase hex and nothing else; the importer refuses a handoff that names anything but its own PSP (`air.psp_did`), a URL, a name, another DID or capitals included, with `Invalid` and nothing added.
- **Statuses.** Reply body = the route's JSON. A `400` is `STATUS_REFUSED` with that JSON, read by the same code (`Refused`; a refused issue or spend is cancelled and its notes freed). Any other `4xx` is `STATUS_REFUSED` with `"http_status": N` and is a plain `Mint` error, so nothing is cancelled. A `5xx` is `STATUS_UNAVAILABLE`, the `502` of an ESP mint that does not answer included: the request stays pending, and the retry is the same request, answered from the stored answer.
- **Kept requests.** An FSP call is kept in `air_requests` by (mint DID, kind, body hash), like the others; an issue is found by its request hash, a spend by its notes (fsp-mint's own idempotency).
- **No HTTP is left in the wallet.** `src/http.rs`, the `http` feature, `reqwest` (now a dev-dependency of `redeem_flow` only), `--fsp-url`, `$ECASH_FSP_URL` and `DEFAULT_FSP_URL` are gone.

### The reply DID

Every PSP purchase has a reply DID of its own: the public half of a key `build_psp_payload` makes for it (a made-up shared stand-in used to be kept in the wallet file as `reply_did`; that field, `Wallet::reply_did()` and `buy-psp --reply-did` are gone, and a file that still has the field reads, ignoring it). One key per purchase means the PSP cannot link two purchases of the same wallet. The secret is saved with the pending purchase, and the PSP's record is sealed to its public half. The reply DID has to be a key for the PSP to seal to; a payload whose reply DID is not (the field is the payer's to fill in) cannot be delivered, and psp-mint marks that delivery abandoned.

## Tests

`cargo test` runs:

- **Blinding.** An unblinded signature verifies against the mint's key. A wrong key or wrong blinding factor does not.
- **Note file.** A change is saved before the call returns. A reopened wallet has the same notes. A corrupt file is an error and is not replaced. The file is `0600`.
- **PSP.** A payload round trip: build, decrypt with the mint's key, decode, and the outputs match. A payload sealed to another key does not decrypt. Claimed signatures become notes the PSP accepts. A partial claim leaves the rest pending. A signature cannot be claimed twice. A bad claim changes nothing. The denomination and output-count limits.
- **ESP.** The request is always exact: the PSP notes spent, times 10^11, equal the outputs' total, with and without change. The cover is the exact set when one exists and otherwise the tightest the wallet can find, checked on several holdings. The memo and request hash match the ESP mint's. Spend signatures cover the memo. A refused exchange frees the reserved notes. A finished one swaps PSP notes for ESP notes, change included. The asked-for split must add up. Not enough PSP, and an exchange below 1 PSP, are refused before anything is reserved. **Spent elsewhere.** `mark_spent_elsewhere` moves the notes the mint names out of the balance into the spent record and frees the others, survives a reopen, leaves them out of later exchanges, and changes nothing when the mint names no note, a position the request lacks, or an exchange the wallet does not have. `exchange_refusal` reads the mint's `400` body: the spent-elsewhere answer carries the positions, and every other `400`, or a body that does not say so, is an ordinary refusal.
- **`tests/flow.rs`, in one process, with `air-listener-tests`** (the exchange goes the way a wallet sends one: `build_exchange`, then `send_exchange` over AIR to a real esp-mint listener, whose PSP is a stand-in over the PSP mint in the process). Build the payload, reopen the wallet, open the payload as the mint does, settle it with the PSP's real settlement code, read the delivery record and apply it (`apply_delivery`), check every note with the PSP's own check, then exchange: 3 PSP from a 4 and a 1 (the 4 is spent, 3 PSP of ESP plus 1 PSP of change), a request made one ESP unit off is refused (the mint's "an exchange must be exact" refusal, short by the extra unit) before anything is burned, and the last 1 PSP is exchanged exactly. Every ESP note, change included, is checked against the key the mint derives for its terms. A retry gets the same reply and burns nothing more. Also: a payload sealed to another key is ignored and leaves no record, a payload with any one byte flipped is ignored, an exchange without enough PSP is refused before anything is reserved, and a signature the wallet did not ask for is refused.
- **Receiving a hand-over** (`src/transfer.rs`). `pick_exact` finds a set that adds up exactly and only then. Receiving checks each spend secret against its note and refuses a duplicate, an empty hand-over and a note that names no keyset (`tests/keyset_refusals.rs`: sp-wire's `Handover::read` refuses the file without a `keyset` ("missing field") and the one with an empty keyset ("note 2 of the hand-over file names no keyset"), and the wallet's own check refuses the empty keyset in a typed hand-over, each with the wallet file unchanged). `tests/redeem_flow.rs` takes the whole way: the customer's ESP goes to a real fsp-mint (two days, one long past and one far ahead), `fsp_mint::export::export_esp` writes the files, the service's wallet takes them in with `receive_handover` (the notes, service, days and keysets are what fsp-mint kept), receiving a file again is refused and changes nothing, and the redemption at the real esp-mint takes the mature notes and leaves the others.
- **`tests/fsp_flow.rs`, in one process, with a real esp-mint behind its real AIR listener and fsp-mint's `AirIssuer`** (the wallet's calls to the FSP mint go to fsp-mint's own real listener on the same `air_server`, under an `air.fsp` entry). Issue FSP from ESP of mixed days, pay with change, the automatic rollover after a rotation (staggered, then swapped without a prompt), a crash after the mint answered finished from the stored answer, offline within the window rolls over and beyond it is lost, a failed rollover (a signed "cannot answer now" for the spend) logged and retried on the next connection, a refused spend (memo over the mint's limit) that cancels the request and frees the notes, an ESP mint that does not answer fsp-mint leaving the issue pending and the retry finishing it with the ESP transferred once, a service with no `air.fsp` entry refused naming the setting (in the library and in the command, which also has no `--fsp-url`), and the ESP schedule.
- **FSP refusals that name spent notes** (`src/fsp.rs`, `tests/fsp_flow.rs`). A refused payment marks exactly the named notes spent, frees the others and drops the request; a refused rollover does the same and returns a log line, and the next rollover leaves the spent notes out; a refused issue counts the positions across the groups; a refusal that names a position the request does not have, or none, is a mint error that cancels the request, marks nothing spent and frees its notes (for a payment, a rollover and an issue; the library call `mark_spent_in_fsp` itself refuses such positions and leaves the wallet unchanged). The integration test runs it against real mints: a spend whose reply was lost is cancelled, a new spend picks the same notes, the mint names them, and the wallet ends with them spent and the rest payable.
- **Owed PSP credit and the redeem split** (`src/psp.rs`, `src/redeem.rs`). The credit is summed over open purchases, left out once the window closes, and printed in PSP and USD; a ceiling too small for one note names the limit in force, and the plan's summary comes before its `not sent` lines.
- **Spent notes the mint names** (`src/redeem.rs`, `src/transfer.rs`, `src/rotate.rs`, `src/esp_replies.rs`, `tests/redeem_flow.rs`). `refuse_redemption` moves the notes a `below_fee` refusal calls `already_spent` to the spent record, flags a bad proof, frees the rest, and with no list just frees the notes. `mark_spent_in_rollover` does the same for the positions the mint names, and refuse a position the request lacks. The refusal bodies are read (`redeem_refusal`, `exchange_refusal`, and the rollover reader, with no stray `: ` when the mint sends no code). `tests/redeem_flow.rs` runs it against a real esp-mint: a copy of a spent note is refused `below_fee`, moved to the spent record, and not offered again.
- **Single error print** (`src/main.rs`). A failed redemption request is printed once, by `main`; later failures get their own line.
- **Handoff** (`src/handoff.rs`, `tests/handoff_flow.rs`). The base-44 codec round-trips every length and uses only the QR alphanumeric characters. A PSP handoff is sealed to a DID key and round-trips; only that key opens it (another key is refused with nothing written); an unsealed one, one with a DID key or FSP in it, and an FSP body under the PSP prefix are refused. An FSP handoff with two services and a DID key round-trips, adds the very notes the sender held, and is never swapped; a body without its DID key, without groups, with bytes after the key, or a PSP body under the FSP prefix is refused. A string under the other kind's prefix is refused, as is the old `SPH1:`. Export refuses the wrong kind of note for each handoff, a note twice, nothing, an inexact amount and a held-back note. Sizes are as documented. Whitespace and case are forgiven; a damaged, cut or extended payload, another version, a forged secret, a retired key set, a non-power-of-two amount and a second import are refused with nothing added. Cancel returns the notes; done drops them. `tests/handoff_flow.rs` runs it against a real psp-mint (a PSP handoff opened with the right key only, swapped and final; the same string refused by the mint a second time; cancel; **a swap that cannot be sent leaves the PSP unswapped but in the balance and spendable, and the next sync swaps it; a note spent before the swap is sent is left out of it and the rest is swapped; reclaim before the receiver swaps (the sender gets fresh notes, burns the handed-off ones, and a late receiver is told they are spent and loses them from the balance), reclaim after the receiver swapped (nothing comes back, the handoff is done), a note spent elsewhere (check says partly, the rest is reclaimed, and a receiver drops the spent one and swaps the rest)**) and a real esp-mint and fsp-mint (FSP and a DID key to a wallet that has never seen the mint, not swapped, grouped by service, and spent at the mint). An FSP handoff that names anything but the service's DID in hex as its mint is refused.
- **Merge** (`src/merge.rs`). A copy of another network, or a file with no network, is refused and the wallet is unchanged. The version counter goes up on every write. Two diverged copies are united in both directions with the same result. A stale copy cannot revive a spent, lost or handed-off note, and a cancelled handoff comes back. A new device receives the starter notes. Pending requests are united once; a finished request is not revived. Merging a wallet with itself changes nothing and writes nothing.
- **Settings** (`src/config.rs`). The defaults are local only and round-trip through `get` and `set`. The file is read, then the environment wins, each value with its source. A named file must exist and `--config` beats `$ECASH_CONFIG`. A list in the file is an array or one string; an empty list is local only. A duplicate, an empty entry, a bad key, a number in the list, an unknown setting and bad TOML are each refused, all listed together. `storage.wallet` is the wallet-backup list only; it is not the service FSP fees are paid to.
- **Settings, AIR** (`src/config.rs`). The server and the host are required for every call to the PSP or the ESP (`AirSettings::require` names the missing ones and the variables that set them); with the file and the environment and their sources; one without the other is an error naming the one missing, and so is a DID without both; the tuning settings alone leave the connection unset; a bad server name, DID, host (a URL, a port, a space) or number is refused naming the setting; every spec has its own variable.
- **The PSP's mint info over AIR** (`tests/air_flow.rs`, with `air-listener-tests`; a real `air_server` in the process and psp-mint's real listener). The wallet verifies over AIR and leaves nothing pending; a PSP on another network is refused with the network check's error and the request ends; a request with no listener is kept in the file (and survives a reopen) and a later call picks up the reply without writing a second request; a reply found an hour after it was issued is dropped and a new request answered; a tampered reply is refused and the request dropped; a PSP that dies after opening the request is retried and ends with one reply; keys, keysets, the rotation window, the largest note size, the keys to claim with (no keyset printed, a live keyset, a retired one) and a rotation sync over AIR are what the mint's state says they should be, the requests ending as they are answered; a kept mint-info request is not taken for a keys request, and a kept keys request is resumed; tampered, forged, wrong-signer and not-keys replies are refused and the request dropped; a PSP that cannot answer says so at once; without `air.server` and `air.host` no call to the PSP is made, the error names the missing settings, and nothing is written to the AIR.
- **Wire version** (`src/mint_info.rs`, for all three mints). A mint that reports another `wire_version`, or none, or one that is not an integer, is refused with a message naming both numbers and saying nothing was sent. The version is checked before the network. A matching mint passes. `src/date.rs` has the date parser's known answers and refusals.
- **Note limits** (`src/esp.rs`, `src/mint_info.rs`). The exchange limit is the mint's, read from `/fees`; with none read the wallet checks nothing of its own.

The regtest runs in [REGTEST.md](REGTEST.md) are the end-to-end tests with a real Bitcoin node.

- **The ESP's calls over AIR** (`tests/esp_air_flow.rs`, with `air-listener-tests`; a real `air_server` in the process and esp-mint's real listener, built with the same `serve` as `esp-mint serve`, ; a stand-in PSP for the exchange). Mint info, keysets, fees and the rotation window are what the mint's state says they should be; a rollover, an exchange and a redemption end with the notes, the balance and the pending records they always did; one sent twice gets the stored answer and is applied once; a `400` is a refusal and a refused exchange is cancelled, while a `409`, a `413` and a `404` are plain mint errors that cancel nothing; an ESP that cannot answer says so at once; a tampered reply, a forged one and a reply of another kind are refused and the request dropped; a request to the PSP's DID and one to the ESP's, for the same kind, are kept apart; without `air.server` and `air.host` no call to the ESP is made and the error names the missing settings; the built-in placeholder ESP DID is never passed silently.

## Command line behaviour

On a `400` the exchange frees its notes. The exception is a request the mint says had notes spent by a different request: those notes are marked spent (they leave the balance and `balance` prints "spent elsewhere N note(s)"), and the request's other notes are freed. The mint names them in the refusal (`code: note_spent_elsewhere`, `spent`: positions in the request) on an exchange and a rollover (PSP and ESP), and on an FSP spend, rollover or issue (`mark_spent_in_fsp`). A redemption refused for being `below_fee` carries a reason for every note (`notes`), and the wallet moves the notes marked `already_spent` to its spent record, flags the ones marked `bad_proof`, and frees the rest. On any other failure it keeps the request and prints the `--resume` command.

**Note limits.** The wallet holds no limit of its own for ESP, and none for the largest PSP note: `buy-psp --sync` reads the PSP's top denomination from its keys over AIR (the highest amount with a key, `mint_info::sync_psp_limits`) and refuses a larger size; offline it checks only that the size is a power of two and the PSP decides the top. Before an exchange it reads `exchange.max_items` from the ESP's fees over AIR (`mint_info::sync_esp_limits`) and refuses a request over them, naming the mint's setting. Offline it builds the request and lets the mint decide. The one count the wallet does hold is `psp::MAX_OUTPUTS`, 255 outputs in a purchase: that is not a setting but the payload format, whose output count is one byte.

*Why mainnet by default:* the default should be the network a real user is on; development passes a flag.
