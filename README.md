# ecash-wallet

One wallet library for PSP, ESP and FSP (Primary, Encumbered and Fast Service Points), with a thin command line. AIR apps embed the library. The command line only parses arguments and prints, so everything it does is a call into the library.

The library holds no BTC wallet. The app's own Bitcoin wallet puts the bytes from `build_psp_payload` in an OP_RETURN and pays.

## Status

Built and tested: the library, the command line and the end-to-end regtest runs in [REGTEST.md](REGTEST.md) (steps 0 to 49: purchase, claim, exchange, transfer, redemption, FSP, refusals, splitting, and key rotation). What each release contains is in [CHANGELOG.md](CHANGELOG.md). What is not built is in [ROADMAP.md](../sandbox-mint/ROADMAP.md).

## Setup

The wallet builds from tagged dependencies: mint-core at `v0.1.3` and `sp-wire` at `v0.4.0` (git tags), and, through `sp-wire`'s `seal` feature, the `air` crate at commit `8e281d5` (AIR 2.0.3; no AIR tag exists at that commit). The next sp-wire moves it to AIR 3.0.0 (commit `ff41c09`; AIR's only tag is `v2.1.0`, so 3.0.0 is pinned by commit) with the same sealed bytes and the same key types, and the wallet's code does not change for it. **It does not depend on the mint crates.** Every type it exchanges with the mints, the PSP payload and its encryption, the request hashes, the unit constants and the error codes come from `sp-wire` (see "Wire format and versions"). The mints (`psp-mint` `v0.3.0`, `esp-mint` `v0.5.0`, `fsp-mint` `v0.4.0`) are dev-dependencies only: the tests start real ones in the process, and nothing in the library or the command line links them.

AIR has no path dependencies, so nothing needs patching to build it from git as it is. AIR 3.0.0 does not export `SecretKey` yet, so until the next sp-wire is tagged and its AIR pin is a commit that does, the wallet is built against the local `sp-wire` and AIR folders with a git-ignored `.cargo/config.toml` (sp-wire's README shows the AIR block). The repo's committed `Cargo.lock` keeps sp-wire at `v0.4.0` and cargo then reports the patch as "was not used", so run `cargo update -p sp-wire` once after adding the patches, check that `cargo tree --all-features -i air` shows the local AIR folder, and run `git restore Cargo.lock` before committing (a lock file that names a local path would not build from GitHub). To test against unpushed local copies of `sp-wire`, the mints or mint-core, `source ~/sandbox-mint/scripts/local-git.sh` points git at the local folders and their local tags.

```
cd ~/ecash-wallet
cargo test
```

The wallet makes no HTTP call, and there is no `http` cargo feature (the HTTP client and `reqwest` are gone; `reqwest` is a dev-dependency of `redeem_flow` alone, which calls the in-process ESP mint's operator routes). Every mint, the FSP mints too, is reached over AIR only, and there is no `air` feature to turn off: the library always builds sp-wire's `air-client`, which builds `air_server`. `air_server` names AIR as `path = "../air"` (upstream issue 3), so building takes a local patch for it beside the AIR one in the git-ignored `.cargo/config.toml`, and the AIR patch must be the folder `<air_server>/../air`, or two `air` crates are built and their types do not match. For now both are the sandbox checkouts (`.../sandbox-mint/air-sandbox/air` and `.../air_server`; sp-wire's README, "The AIR request", shows the blocks). `cargo update -p sp-wire` and `git restore Cargo.lock` apply as above.

The wallet file holds spend keys. Losing it loses the notes and the blinding factors for anything in flight. A missing file is an empty wallet; a file that cannot be read is an error and is never replaced. More in [DESIGN.md](DESIGN.md), "Notes and the wallet file".

## The PSP's calls over AIR

Six calls to the PSP go over AIR, and only over AIR. The first four are read-only: its **mint info** (what `wire_version` and `network` report, which the wallet asks before it sends anything to the PSP), its **keys**, its **keysets** and its **rotation window**. The other two have a body, and the first changes state: its **rollover** (the swap of old-keyset notes for new, sent by the rotation sync, on import of a handoff and on reclaim) and its **check-state** (`handoff check` and the check inside `handoff reclaim`). **`air.server` and `air.host` are required** (the DID is the SPI's: built in, or `air.psp_did`): the wallet writes a small sealed request into a mailbox of the PSP's DID on the configured AIR server and verifies the PSP's signed reply (the signature is the PSP DID key's, checked against the 33-byte DID alone). The reply body is the JSON the PSP's operator route used to return, so the wallet reads it with the types it already uses. Without the two settings every one of these calls stops with an error naming them. The PSP has no HTTP calls left in the wallet. The wallet's own files never go over AIR.

- **Where the calls are made.** The keys are read when the wallet learns the PSP's largest note size and live keysets (`buy-psp --sync`), and when it keeps notes on a live key set (`rotation_sync`, at startup and in `handoff reclaim`: the rotation window). The code that picks the way is `mint_info` (`psp_keys`, `psp_keysets`, `psp_window`, `sync_psp_limits`, `rotation_sync`, `reclaim_handoff`).
- **The PSP delivers each purchase over AIR; there is no paste.** `buy-psp` makes a one-off reply key for the purchase, puts its public half in the payload as the reply DID and saves the secret in the wallet file next to the pending purchase, before the payload is shown (so the PSP cannot link two purchases, and the key is on disk before any payment). When the PSP settles the payment it writes one record, signed by its DID key and sealed to that reply DID, on the AIR server (`air.server`/`air.host`, the same as the PSP's). It holds the signatures and the PSP's live keysets (so the wallet needs no keys call), or says the payment is held, or gives the reason the purchase was rejected, with what the PSP received. The record is at an address only the wallet and the PSP can compute (the PSP's DID, the reply DID and the purchase: `sp_wire::air_request::delivery`), and it is write-once. `claim-psp` reads the address of every pending purchase (waiting up to `--wait` seconds, 60 by default, for the ones not there), checks the PSP's signature, claims the notes and clears the purchase. A held payment or a rejection does not clear it: the wallet shows the reason and what was paid, and keeps the purchase and its key open until the PSP's reconciliation window closes (the record says when, 7 days by default at the PSP; the wallet has no setting for it). If the PSP has not settled it by then it forfeits the payment and keeps the bitcoin, and the wallet deletes the purchase and its key, at the start of any command. What would settle it (a corrected request, or a credit) is not built yet. A purchase with no readable reply key at the PSP gets no record, and the payer takes the loss. Every command also tries once when it starts, if a purchase is pending (a note if `air.server` or `air.host` is missing). Reading the same record twice changes nothing. A purchase made before this release has no key and cannot be picked up (`claim-psp` says so); a purchase that is owed a credit (an overpayment), or whose outputs the record neither signs nor reports as dropped, keeps its key in the wallet file after the notes are claimed, because the PSP will write a follow-up record to it (that follow-up is not built yet; a short payment that the record accounts for is closed). That key is deleted when the PSP's window for the credit closes, or a week after the record when none was named.
- **What the signed reply adds.** The keys come in a reply signed by the PSP's DID key, so nothing in between, not the AIR server and not a man in the middle, can substitute keys.
- **No caching.** Every call asks again; nothing is remembered between calls except the run's first mint-info answer (below).
- **A PSP that cannot answer** (its mint lock is poisoned, a rotation step failed) says so in a signed reply, and the wallet fails at once with "could not answer keys now" instead of waiting out its tries.

- **The request is kept in the wallet file** (`air_requests`: the request kind, the request id, the one-off key, the slots written) from before the first write until it is answered, so a reply that comes while the wallet is not looking is read on the next call without writing a second request.
- **Retry:** 3 tries of 30 s (`air.attempts`, `air.reply_wait_secs`), the same request each time in the next free slot; then "the PSP did not answer over AIR" and the request stays. The next call of the same kind carries on with it (one kept request per PSP and kind).
- **A reply that fails a check ends the request** and says what was wrong: a network or wire version that is not this wallet's is the `Wire` error that names both numbers; a bad signature, another mint's, another request's, or a bad body is "a reply that was refused". A reply older than `air.max_skew_secs` when it is found is dropped and one new request is made in the same call.
- **The command line asks once per run** (the first answer is kept for the run): with the PSP down, AIR costs 3 x 30 s once, not at the startup check and again at the command.
- **Rollover and check-state.** The request JSON is the request body, sealed to the SPI's DID with the rest of the request (the notes in it are readable by the mint only), and the reply body is the JSON the mint returns. A signed refusal is the wallet error for a `400` refusal (`Refused`, `SpentElsewhere` with the positions), so a refused rollover is cancelled and its notes freed, and spent notes are marked,. A rollover sent again is **not applied twice**: the mint answers a body it has already answered from what it stored. The kept request is found by its body (its SHA-256 is kept with it), so the same rollover resumes and a different call never takes its place. The ceilings are the mint's ( 1 MiB and 1000 notes by default); a chunk of 1000 notes is about half a megabyte.
- **The built-in SPI DID is a PLACEHOLDER.** The wallet ships with the SPI's DID built in (`config::BUILTIN_SPI_DID`), and `air.psp_did` overrides it. The ESP has its own (below). Until the first SPI deploy puts the real one in (sandbox-mint OPERATIONS.md, "First SPI deploy", step 0) it is a point with no known private key: nothing sealed to it can be read and no reply from it can verify. It never passes silently: while it is in use the wallet prints a warning at every start and in `config`, and a call that fails says the DID is the placeholder.
- `ecash-wallet config` shows which way the PSP is asked.

## The ESP's calls over AIR

The ESP's wallet-facing calls go over AIR the same way as the PSP's, and only over AIR (`air.server` and `air.host` are required), to the ESP's own DID (`air.esp_did`, else the built-in one): its **mint info**, **keysets**, **rotation window** and **fees**, and the four calls with a body, **rollover**, **exchange**, **transfer** and **redeem** (whose body is the canonical binary encoding). The reply body is what the ESP's operator route used to return, so the wallet reads it with the code it already has. The ESP has no keys call (its keys arrive in the replies), and its `GET /audit` and `GET /health` are the operator's and the SPI's own, local to the ESP's machine: the wallet does not call them. The ESP's melts and burns with the PSP are between the two mints and are not the wallet's.

- **Two mints, two DIDs, one AIR server.** The PSP and the ESP each have their own DID (their own `mint_did_key.json`), and the same local AIR server and host can serve both, so one pair of settings serves both. A kind names a call, not a mint: the wallet sends the same kind (fees, say) to either DID and each answers in its own shape. Requests kept in the wallet file are found by DID, kind and body, so the two never meet.
- **The built-in ESP DID is a PLACEHOLDER**, like the SPI's: `config::BUILTIN_ESP_DID` is a point with no known key (and not the SPI's), replaced at the first SPI deploy. While either placeholder is in use the wallet warns at every start and in `config`, and an unreachable mint's error says which DID was the placeholder and which setting replaces it.
- **Sending an exchange, a transfer or a redeem again is safe.** The ESP stores its answers by request hash, so a request resent after a lost reply gets the stored answer and is not applied twice. If the wallet crashes between writing the request and reading the reply, the next call finds the kept request by its body and reads the reply cell first.
- **Refusals.** A `400` is a signed refusal with the mint's JSON, read by the same code (`Refused` or `SpentElsewhere` for an exchange or transfer, `RedeemRefused` for a redemption; a redemption's `413` too), so a refused exchange is cancelled and its notes freed, as before. A `409` (the same request is being answered), a `413` on exchange or transfer or a `404` (rotation on a mint that does not rotate) come as refusals that carry `"http_status": N`; the wallet reads those as a plain mint error, never as a refusal of the notes, because the outcome may be unknown and the request is to be sent again. A `5xx`, the `502` of an ESP that cannot reach the PSP included, is a signed "cannot answer now".
- **Privacy.** A request is sealed to the ESP's DID with everything in it, so the notes in an exchange, transfer or redemption are readable by the ESP only, not by the AIR server; the reply is sealed to the wallet's one-off key. The size ceilings are the ESP's own, unchanged.
- **The ESP answers one request at a time** over AIR (in slot order), because an exchange talks to the PSP; a slow exchange holds up the requests behind it. The wallet's tries and waits cover this.
- **To get a working setup**, the ESP needs esp-mint's `air.*` settings and its DID key (`esp-mint pubkey` prints the DID to put in `air.esp_did`).

## The FSP mints' calls over AIR

A service's FSP mint (fsp-mint) is reached over AIR too, and only over AIR; the wallet has no HTTP client left. There is one mint for each service, so the wallet needs, for the service a command names, the **`air.fsp` entry** `<service DID>@<AIR server key>@<host>` (the DID the requests are sealed to and the replies are signed under, the AIR server the mint's own listener is on, and where it is). `fsp-mint serve` prints the entry when it starts. The calls are the kinds the ESP already has, mint info (1), keys (2), rotation (4) and fees (7), and two new ones, **FSP issue (11)** and **FSP spend (12)**, whose bodies are the JSON the mint's `POST /issue` and `POST /spend` took. A kind names a call and the DID picks the mint.

- **A service with no `air.fsp` entry is refused before anything is sent**, with an error that names `air.fsp`, `$ECASH_AIR_FSP` and the service. The same holds for `fsp sync` and `fsp-window`, and for the sync at startup, which logs the refusal for a service it has no entry for and tries again at the next start.
- **The reply body is the route's exact JSON**, with the same size ceilings. A `400` is a signed refusal with the route's JSON: an issue or spend that is refused is cancelled and its notes are free again, as before. Any other `4xx` is a refusal that carries `"http_status": N` and is a plain mint error (the outcome may be unknown; the request is sent again). A `5xx` is a signed "cannot answer now", the `502` of an fsp-mint whose ESP mint does not answer included.
- **A pending issue stays pending when the ESP mint does not answer fsp-mint.** The FSP mint says so in a signed reply, the wallet keeps the request, and the next `fsp sync` (or `fsp issue`) sends the same request: fsp-mint answers it from the answer it stored by request hash, so the ESP is transferred once and FSP is issued once. A spend is likewise found again by its notes.
- **The requests kept in the wallet file** (`air_requests`) are found by the mint's DID, the kind and a hash of the body, so a reply that comes while the wallet is not looking is read on the next call without a second request.
- **The wallet's records of an FSP mint are keyed by the service**, not by a URL. Wallet files from before still read: the `url` an FSP mint record carried is ignored, and the swap schedule entries keyed by a URL are left alone and harmless.

## Wire version

Every mint reports `wire_version` (every mint's mint info, over AIR), and the wallet refuses a mint whose number is not its own (`WalletError::Wire`, naming both). The types come from [`sp-wire`](../sp-wire/README.md). Details in [DESIGN.md](DESIGN.md), "Wire format and versions".

## Command line

**Network.** The wallet is on mainnet unless given `--regtest`, `--signet` or `--testnet` (`--mainnet` may be given; at most one). Before it sends anything to a mint it asks the mint (its mint info, over AIR) which wire version it speaks and which network it is on, and stops if the mint is on another wire version or network or does not say; nothing is sent. Every walkthrough below passes `--regtest`. The wallet file is per network (see "Notes and the wallet file").

```
ecash-wallet [--wallet FILE] [--config FILE] [--regtest|--signet|--testnet] <command>
```

| Command | What it does |
|---|---|
| `buy-psp --mint-key HEX [--sync] AMOUNT...` | Makes the purchase's one-off reply key and saves it in the wallet file, then prints the encrypted payload as hex on standard output and the purchase id on standard error. With `--sync` it first reads the PSP's live key sets and its largest note size over AIR; the payload names the PSP's key set, and a size above the PSP's largest is refused. Without it the payload names the key set the wallet last saw, if any, and only the power of two is checked. |
| `claim-psp [--wait SECONDS]` | Reads the PSP's delivery record for every pending purchase over AIR, waits up to `--wait` seconds (60 by default) for the ones not there, claims the notes and clears the purchases. A held or rejected purchase is shown with its reason, what was paid and until when it stays open, and is not read again; it is not an error. Says which purchases were not delivered, and exits with an error if any was not. It takes no signatures: `--file`, standard input and `BLIND_NONCE:SIGNATURE` pairs are gone. |
| `exchange --service DID --psp N [--amounts A,B,C] [--resume ID]` | Exchanges at least N PSP (N is 1 or more) for ESP bound to a service (its 33-byte AIR DID, 66 hex characters; the old 32-byte x-only form is refused with a message that says so). Whole PSP notes are spent and the difference comes back as ESP change. ESP notes are powers of two, so the amount and the change are each split into the fewest of them (`--amounts` picks other sizes, each a power of two, with the same total). `--resume` sends a pending request again. There is no command to split ESP you hold: convert it to FSP straight away (see DESIGN.md). |
| `hand-over --service HEX (--esp UNITS \| --psp N) [--day D] --out FILE` | As the app: take whole ESP notes for that service that add up to exactly the amount out of the wallet and write them, with their spend secrets, to a new file (`0600`; an existing file is never replaced). Refused if no set of notes adds up to the amount. |
| `receive FILE` | As the service: take a hand-over file into this wallet. |
| `transfer --service-key HEX [--day D] [--amounts A,B,C] [--resume ID]` | As the service: swap every free ESP note this wallet holds for the service (the one the 32-byte secret key belongs to) for fresh notes of the same total, split into the fewest powers of two. `--amounts` chooses other sizes, each a power of two, which must add up to the same total. `--resume` sends a pending request again. |
| `balance` | PSP, ESP (by service and day) and FSP held, and what is waiting. |
| `config` | The settings in use and where each came from. |
| `redeem --service-key HEX --memo TEXT [--max-bytes N]` | As the service: redeem every mature free ESP note for that service (mixed days allowed) for a payout to TEXT. Reads the rate and ceiling from the ESP's fees (an AIR call), prints each request's size and fee, splits over the ceiling, and on `refund_required` or `outputs_over_limit` rebuilds from the mint's totals and sends again. |
| `redeem --service-key HEX --resume ID` | Send a pending redemption again after a lost reply or fault. |
| `redeem --collect` | Ask about every redemption waiting for payout: completed ones end, declined ones give back the reissued notes with the reason. |
| `fsp issue --service HEX [--esp UNITS \| --psp N]` | Issue FSP from this wallet's free ESP for the service (all of it if no amount). `--service` is always needed, for `fsp pay` and `fsp sync` too; there is no default (`storage.wallet` is the wallet-backup list, not the service FSP is paid to), and without it the command refuses. |
| `fsp pay --service HEX --units N [--memo TEXT]` | Pay N FSP units to the service, with change. |
| `fsp sync --service HEX` | Finish pending FSP requests and roll previous-keyset FSP over now (it also happens on every connection and at startup). |
| `fsp-window --service HEX` | Print the FSP mint's rotation schedule (an AIR call, kind 4). |
| `handoff export-psp --to DID --psp N [--out FILE]` | A **PSP handoff**, a developer to a user (for example after an in-app purchase): take free PSP notes adding up to exactly N out of this wallet and print them as one string (`SPHP1:...`), sealed to the recipient's DID public key `DID` (66 hex characters), so only the holder of the matching secret key can open it. It carries PSP only, never a DID key or FSP. The warning and the size go to standard error. See "Handoff between wallets". |
| `handoff export-fsp --fsp SERVICE:UNITS... --did-key-file FILE [--out FILE]` | An **FSP handoff**, to your own new device: a little FSP (enough to pay to fetch your wallet from the AIR) and your DID secret key from `FILE` (64 hex characters), as one string (`SPHF1:...`). **Not encrypted**, because it carries the key it would be encrypted to: anyone who sees it can spend the notes and act as your DID. |
| `handoff import STRING\|FILE\|- [--did-key-file FILE] [--did-key-out FILE] [--from NAME]` | Take a handoff in; the kind is read from its start. Checks it, refuses one imported before and the old `SPH1:` kind, and records where the notes came from. A PSP handoff needs `--did-key-file` (the secret key of the DID it was sealed to). Its notes are **in the balance at once** and are **always swapped** at the PSP mint for notes only this wallet knows, now and at every start while the mint cannot be reached (`balance` shows how much is still unswapped). An FSP handoff is **never swapped**; its DID key is written to `--did-key-out` (`0600`, never replaced) and is refused without it. |
| `handoff check ID` | Ask the PSP mint where a PSP handoff you made stands, from its record of which notes are spent: **none** (still yours to reclaim), **all** (the receiver swapped or spent them: the handoff is done) or **some** (those are dropped from the record, the rest can be reclaimed). |
| `handoff reclaim ID` | Take back what is left of a PSP handoff the receiver has not swapped: swap the notes back to this wallet at the mint, for fresh notes only it knows. The mint takes whichever of the two swaps reaches it first; if the receiver was first, the handoff is recorded as done and nothing comes back. Run it again after a crash or a lost reply. |
| `handoff list`, `handoff cancel ID`, `handoff done ID` | The handoffs made and imported. `cancel` puts an unclaimed handoff's notes back **without asking the mint** (use `reclaim` for a PSP handoff). `done` drops them once you know the other wallet has swapped. |
| `merge FILE` | Merge a wallet file retrieved from storage into this wallet (see "Merging two copies of a wallet"). |
| `esp-schedule [--by YYYY-MM-DD]` | ESP mature now, mature by the date, and by month, from the wallet's notes (all services). |
| `migrate` | Move a pre-network `~/.ecash-wallet/wallet.json` to `regtest/`. |

No mint has a URL: the PSP and the ESP are reached over AIR through `air.server` and `air.host`, and a service's FSP mint through that service's `air.fsp` entry. `--psp-url`, `--esp-url` and `--fsp-url` (and `$ECASH_PSP_URL`, `$ECASH_ESP_URL` and `$ECASH_FSP_URL`) are gone.

`--service-key` is a secret key, passed on the command line only because this is a development tool. A real service keeps its DID key in the AIR and never types it. Shell history keeps what is typed, so use it for test keys only.

## Handoff between wallets

A handoff moves notes from one wallet to another as one string, with no AIR, mint or network in between (a QR code works too: see below). There are exactly two kinds. The API, the command line and the string format make every other mix impossible, and a hand-made one is refused.

| | PSP handoff | FSP handoff |
|---|---|---|
| For | a developer to a user, after an in-app purchase | one person's old device to their new device |
| Carries | PSP notes only | FSP notes and the DID secret key |
| Encrypted | always, to the recipient's DID public key | never (it carries the key it would be encrypted to) |
| On import | in the balance at once, and always swapped at the PSP mint, no opt-out | never swapped |
| Taken back | `handoff reclaim` (the mint decides who wins) until the receiver swaps | `handoff cancel` (local only) |
| Starts with | `SPHP2:` | `SPHF2:` |
| Made with | `handoff export-psp --to DID --psp N` | `handoff export-fsp --fsp SERVICE:UNITS --did-key-file FILE` |

The old combined `SPH1:` handoff of 0.4.0 (PSP, FSP and an optional key, swapped only if asked) is refused with a message that names the two new kinds.

**PSP handoff.** The notes' spend secrets are sealed to the recipient's DID key with `sp_wire::seal`, which is AIR's own `PublicKey::encrypt` (no new cryptography). The app makes its DID locally and tells the developer's service the public key; the service runs `export-psp`. The user's wallet opens it with the DID secret key, counts the notes in its balance, and swaps them at the PSP mint first thing, whenever the mint can be reached (`POST /rollover`, same amounts): on import, then at every start and on every connection to the mint. The handoff is final for the receiver when the swap succeeds. If the mint cannot be reached, the notes stay **unswapped**: they are in the balance and can be spent, `balance` prints how much of it is still unswapped, and the swap is sent again at every start. There is no lock on unswapped notes, because none is needed: spending a note at the mint burns it exactly as the swap does, so whichever reaches the mint first wins and the other is told the note is spent. A swap whose notes were spent meanwhile is rebuilt for the rest. If the mint says a note was spent already (the sender reclaimed it, or a copy was received first), that note leaves the balance and the user receives nothing for it.

**Reclaim.** While the receiver has not swapped, the sender can take the notes back with `handoff reclaim ID`, and `handoff check ID` says where it stands. Both ask the PSP mint's record of which notes are spent (`POST /check-state`), and the mint decides who wins: a reclaim is a swap of the same notes back to the sender, and the mint takes the first swap that reaches it and refuses the other with nothing burned. All notes spent means the receiver has them (the sender gets nothing, and the handoff is done); none spent means the sender can still reclaim; some spent means those are gone and the rest can be reclaimed (or swapped by the receiver: first to the mint wins). The stored swap is sent again after a crash, and the mint answers a repeat from its record. An FSP handoff has no reclaim: the mint has no record of who holds an FSP note.

**FSP handoff.** For a user setting up a new device that holds nothing yet: the old device hands over the DID key and just enough FSP to pay to fetch the wallet from the AIR. Both devices are one owner's, so nothing is swapped. After the fetch, run `merge FILE` on the wallet you fetched: the small wallet from the handoff and the full one are united, net of the FSP spent on the fetch. The AIR fetch does not exist yet, so the merge is a separate step that runs after it.

**Both strings are bearer secrets**, and an FSP handoff is worse: it also holds the DID secret key and is not encrypted. Hand it over in person or by QR code between your own devices, never post it or send it over a network, and delete it once it is imported. The warning is printed on standard error on every export and every import (`PSP_WARNING`, `FSP_WARNING`).

Reclaim, cancel and done: the notes leave the sender's balance when the string is made. For a PSP handoff, `handoff reclaim` brings them back through the mint, which is the safe way. `handoff cancel` puts them back locally, without asking the mint; if the other wallet already has the handoff, the first of the two to swap or spend wins, so cancel is for a string that was lost or never delivered, and for an FSP handoff. `handoff done` drops the sender's copy once it knows the handoff was claimed.

Size, for the QR code: about 188 + 150 × N characters for a PSP handoff of N notes of one key set with a 22-character URL (the seal adds 80 bytes), and about 166 + 150 × N for an FSP handoff of one service (the key adds 32). One QR code in alphanumeric mode holds about 27 notes at error correction L, or 21 at M. More than that goes in a file (`--out`). The wallet draws no QR code. Pipe the string to a tool: `ecash-wallet handoff export-psp --to DID --psp 5 | qrencode -t ANSIUTF8`.

**`send-psp` is gone.** `send-psp`, `receive-psp`, `sent` and the `psp1` token are removed; the PSP handoff does the same job, sealed to one DID, with the reclaim and check brought over from `sent --reclaim` and `sent --check`. The commands now print a message naming their replacements. **Old records are migrated, not kept:** a wallet file that still has `send-psp` tokens in `sent` (pending, reclaiming, received, conflict, reclaimed) is read as before, and each becomes a PSP handoff record with the token's id when the file is opened (the file is rewritten without `sent` at the next save), so `handoff check ID` and `handoff reclaim ID` work on it, including a reclaim that was stored and not sent. A swap that `receive-psp` stored and did not send is still sent at the next start; `balance` shows it as waiting and does not count it, because the wallet never held those notes' secrets. A `psp1` token string itself can no longer be imported: ask the sender to reclaim it and send a handoff.

## Merging two copies of a wallet

`merge FILE` merges a wallet file retrieved from storage (an AIR backup, a copy from another device) into this one. Notes are united by identity, a note spent or handed off in either copy stays gone, pending requests are united without duplicates, and the wallet file's `version` counter goes up with every change. Details in [DESIGN.md](DESIGN.md), "Handoff, merge and the service ID".

## Tests

```
cargo test --all-features
cargo fmt --check
```

`cargo test --all-features` also runs the tests that need the mints' AIR listeners: every wallet test of a call to a mint goes over AIR (there is no HTTP form of those calls left), against an `air_server` started in the test process (on port 5702, which the AIR client always dials, so the port must be free; the tests in one binary take turns) and the real listeners of psp-mint and esp-mint. `tests/psp_delivery.rs` is a purchase from payment to notes with no paste (settled, delivered, picked up and claimed; a rejection; the AIR server down at settlement and a later retry; a record read twice; a record that is not the PSP's or not for the purchase; a wallet file from before purchases had keys). `tests/air_flow.rs` is the PSP's mint info, keys, keysets, rotation, rollover and check-state, with a request resent and not applied twice, refusals, a tampered or wrong-kind reply, a PSP that cannot answer, no call made when `air.server` and `air.host` are missing, and the placeholder DID. `tests/esp_air_flow.rs` is the same for the ESP (a stand-in PSP for the exchange): mint info, keysets, rotation, fees, rollover, exchange, transfer and redeem, refusals (and the `409`, `413` and `404` that are not refusals). `tests/redeem_flow.rs`, `tests/rotation_flow.rs`, `tests/fsp_flow.rs` and `tests/handoff_flow.rs` run the redemption, key-rotation, FSP and handoff flows the same way (the FSP tests use fsp-mint's `AirIssuer` against esp-mint's real listener, and the wallet's own calls to the FSP mint go to fsp-mint's real AIR listener on the same `air_server`). These use `air_listener` (psp-mint, esp-mint) and `AirIssuer` (fsp-mint), which no tag has yet, so they are built only with the `air-listener-tests` feature (`--all-features` has it); plain `cargo test` skips them and runs `flow`, `keyset_refusals` and `transfer_flow`. They need the patches described under "Setup" and mints that have the listener, which today means the local-mints script below.

The tests run in one process with real mints (psp-mint, esp-mint and fsp-mint are dev-dependencies at their release tags) and no network. What they cover is in [DESIGN.md](DESIGN.md), "Tests". Because the mints are at their tags, a change in a mint is not exercised until the tag moves: before a release in which a mint and the wallet change together, run `sh ~/sandbox-mint/scripts/test-wallet-against-local-mints.sh` (with `SP_LOCAL_AIR` and `SP_LOCAL_AIR_SERVER` set to the AIR and air_server checkouts while the AIR request needs them; the script's header says how), which runs these tests against the esp-mint, psp-mint and fsp-mint folders on this machine without changing any repo (and then fsp-mint's, psp-mint's and esp-mint's tests). The regtest runs in [REGTEST.md](REGTEST.md) are the end-to-end tests with a real Bitcoin node.
