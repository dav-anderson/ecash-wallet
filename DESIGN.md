# ecash-wallet: design notes

How the wallet library works and why. The README has the build, the settings, the command line and the tests; this file has the reasoning and the behaviour of each call. The sections were moved here from the README without changes except where noted in [CHANGELOG.md](CHANGELOG.md).

## Wire format and versions

The request and response bodies, the PSP payload and its sealed form, the key-set ID, the request hashes and digests, the redeem encoding, the unit constants and the error codes are defined in the `sp-wire` crate, shared with the mints, so the wallet cannot drift from a mint by a byte. What stays here is the wallet's own: the note file, coin selection, blinding, the schedules and the command line. Two small things are the wallet's own copies and are not wire format: the date parser for `esp-schedule --by` (`src/date.rs`), and the assumed redemption fee rate and request ceiling used before `GET /fees` has been read (`src/redeem.rs`).

Every mint's `GET /health` returns `wire_version`. `http::verify_mint(url, network)` reads it, along with the network, before anything is sent, and refuses a mint that reports another number or none: `WalletError::Wire`, which says the mint's number and the wallet's and to update whichever is older. The command line calls it for every mint. An app that sends its own requests should call `http::check_wire(url, &health_body)` on the body it gets. **Changing any encoded byte or JSON field in `sp-wire` means bumping `WIRE_VERSION`.**

## Notes and the wallet file

Each note is stored with its spend key, its amount and its terms (an ESP note has a service and a redeemable-after day). The notes, and the requests that have been sent and are waiting for a reply, are one JSON file:

- `--wallet FILE`, else `$ECASH_WALLET_FILE`, else `~/.ecash-wallet/<network>/wallet.json` (`main`, `regtest`, `signet`, `testnet`, from the network flag). *Why per network:* notes of one network are worthless on another, and one file for all of them made it easy to send regtest notes to a mainnet mint.
- A wallet file from before the split (`~/.ecash-wallet/wallet.json`) is refused with a message, never read or moved silently. `ecash-wallet migrate` moves it to `~/.ecash-wallet/regtest/wallet.json` (all development so far was regtest); it moves nothing if the target exists, and never deletes.
- It holds spend keys, so it is created with `0600` permissions.
- Every change is written to a temporary file, fsynced and renamed over the old file, and the directory is fsynced. A change is saved before the call that made it returns. In particular `build_psp_payload` and `build_exchange` save the blinding factors before they hand out the bytes or the request.
- A missing file is an empty wallet. A file that cannot be read is an error and is never replaced.
- The file has a `version` counter (up by one on every write), departure and return counters for notes, a set of finished request ids, and the handoff records. They are what lets `merge` reconcile two copies; see "Handoff, merge and the service ID". Files from before them read as zeros and empty sets.
- Moving the note store into the AIR is deferred. The file is a development placeholder.

Losing the file loses the notes and the blinding factors for anything in flight.

## Library

### PSP

```
build_psp_payload(outputs, reply_did, mint_did_pubkey) -> PurchaseBuild { id, payload }
claim_psp(signatures, keys) -> ClaimResult
```

`build_psp_payload`:

1. Takes the note sizes in PSP (powers of two, at most 255, each no larger than the PSP's largest note once the wallet has read it; a PSP is $0.10, so 10 PSP are $1) and a 33-byte `reply_did`.
2. Blinds each output with a fresh spend key and blinding factor.
3. Encodes the payload with `sp-wire`'s `payload::encode` (reply DID, then each amount and blind nonce).
4. Encrypts it to `mint_did_pubkey` with AIR's secp256k1 encryption (`sp-wire`'s `seal::encrypt`).
5. Saves the pending purchase (the blinding factors and spend keys), then returns the bytes.

`id` is the SHA-256 of the sealed payload. `claim_psp` takes the pairs the PSP prints, `signature <blind nonce> <signature>`, and the PSP's public keys from `GET /keys`. It matches each pair to the pending output by blind nonce, unblinds it and stores the note. It is all or nothing: a pair that matches no pending output, or an amount the PSP has no key for, changes nothing. A signature can be claimed once. When the PSP signed only some outputs (a payment short by more than the price tolerance), the rest stay pending.

`parse_signatures(text)` reads the PSP's printed output. Other lines are skipped, so the whole output can be passed in. `ours(signatures)` keeps only the pairs for this wallet's pending outputs, because the PSP prints every payer's signatures. `discard_purchase(id)` drops a purchase that was never paid.

### ESP exchange

```
build_exchange(psp_units, service, esp_amounts) -> ExchangeBuild { id, request }
finish_exchange(id, response) -> FinishResult
cancel_exchange(id)
```

The mint's exchange is exact, and the smallest exchange is 1 PSP ($0.10, 10^11 ESP), set by the mint's `exchange.min_psp`. So `build_exchange` always asks for the full value of the PSP notes it spends. It picks PSP notes with the smallest total that is at least `psp_units` (exactly `psp_units` whenever some set of its notes adds up to it). The amount asked for becomes the service's ESP notes: `esp_amounts` splits it (default one note of `psp_units * 10^11`, which fits up to 184,467,440 PSP). Anything the chosen notes are worth beyond `psp_units` is added as extra ESP notes under the same terms (the same service and redeemable-after day), so the request always matches. That change is ESP, not PSP, and cannot be turned back into PSP, which is why the wallet looks for the tightest cover. It signs every PSP input over the exchange memo and reserves the notes. `ExchangeBuild` reports `psp_spent` and `change_esp`, and `FinishResult` reports `change_esp`. `finish_exchange` unblinds the mint's reply into ESP notes, each with the service and redeemable-after day, and removes the PSP notes that paid for them. `cancel_exchange` frees the reserved notes, and is only safe when the mint refused the request. After a timeout or a fault, send the same request again: the mint stores its answers by request hash.

`http::fetch_psp_keys(base)` and `http::send_exchange(base, &request)` make the two HTTP calls. A `400` is `WalletError::Refused`. Nothing was burned by the request, with one exception: `NoteSpentElsewhere` means that on a retry the ESP mint found some of its PSP notes spent under another memo (the holder spent them somewhere else), and signed nothing. The `400` body names those notes. `http::exchange_refusal` reads it into `WalletError::SpentElsewhere { why, inputs }`, and `mark_spent_elsewhere(id, inputs) -> SpentReport { marked_spent, freed }` drops the pending exchange, moves the named notes out of the wallet's notes into a record of spent notes (`spent_notes()`), which the balance does not count and exchanges cannot pick, and frees the request's other notes. It changes nothing if the mint names no note, or a position the request does not have. See the esp-mint README, "Burn memos". Anything else that goes wrong is `WalletError::Mint` (the outcome may be unknown).

**Why there is no ESP split.** Only the named service can move an ESP note, so a holder cannot split one, and a payment is a set of whole notes that adds up exactly (see "Transfer to the service"). A way for the holder to split an ESP holding was considered and is not built. A holder converts ESP to FSP straight away, and the FSP mint splits and makes change, so ESP notes are not kept long enough for their sizes to matter. The sizes that do matter are chosen when the ESP is made: exchange in the sizes you will pay (`--amounts`, each a power of two). See esp-mint's DESIGN.md, "ESP amounts are powers of two".

**Why there is no rebuild after a lost wallet file.** The blinding factors of a PSP purchase exist only in the wallet file, so with the file lost the signatures cannot be turned into notes. A way to rebuild is not built, because the AIR keeps the wallet's storage redundant; the local file is a development stand-in (see the ROADMAP).

### Transfer to the service

```
hand_over_esp(service, esp_units, day) -> Handover
receive_handover(&handover) -> (count, units)
build_transfer(service_secret, day, esp_amounts) -> TransferBuild { id, request, esp_units }
finish_transfer(id, response) -> TransferDone { notes, esp_units, redeemable_after_day }
cancel_transfer(id)
```

A payment of ESP is a transfer to the service the notes are named for. The mint swaps the notes for new notes owned by that service, with the same service, the same redeemable-after day and exactly the same total. Nothing is burned out of circulation and no value is created, so the ESP mint's outstanding total does not change. The mint charges no fee (the AIR send fee covers it). Only the named service can ask for the swap, and the app cannot move ESP to another service or to a peer.

There are two sides, and one wallet can play either:

1. **The app (the payer)** calls `hand_over_esp`. A holder cannot split an ESP note, so the payment is a set of whole notes that adds up to exactly `esp_units` (a depth-first search with a budget of 100,000 steps; if no set adds up, it is refused and nothing changes). The notes leave the wallet and become a `Handover`: the service, the day, and for each note its amount, the note and its spend secret. The hand-over is also kept in the wallet file, in case the file is lost on the way. `day` can be left out when the wallet holds ESP for that service with only one day.
2. **The service** calls `receive_handover`. It checks that each spend secret matches its note's nonce, refuses a note it already holds, and adds the notes to its wallet. Then `build_transfer` takes every free ESP note the wallet holds for that service and day and builds the request: it signs each input over the transfer digest with the note's own key, signs the whole request with the service's DID secret key, blinds the new outputs (by default one for each old note, same amounts; `esp_amounts` chooses other sizes that add up to the same total), reserves the old notes and saves the pending transfer, all before it returns the request.
3. `http::send_transfer(base, &request)` posts it to the ESP mint's `/transfer`. `finish_transfer` unblinds the reply into new notes (each checked against the key the mint derives for its terms) and removes the old notes. `cancel_transfer` frees the reserved notes, and is only safe when the mint refused the request (a `400`, `WalletError::Refused`). After a timeout or a fault, send the same request again: the mint stores its answers by request hash, and it reserves the notes of a pending transfer so no other request can take them.

The hand-over file carries spend secrets, so it is written with `0600` permissions and must be given only to the service. It is a file for now. Delivering it as an AIR message to the service's DID is deferred (see ROADMAP.md in sandbox-mint).

### Redemption

```
fetch_redeem_fees(esp_url) -> RedeemFees { fee_per_byte, max_request_bytes, max_memo_bytes }
build_redemption(service_secret, memo, fees, now_unix) -> Vec<RedeemBuild>
send_redeem(esp_url, body) -> RedeemResponse            (or WalletError::RedeemRefused)
rebuild_redemption(id, service_secret, totals) -> RedeemBuild
finish_redemption(id, response) -> RedeemOutcome
cancel_redemption(id)
pending_redemptions() -> &[PendingRedemption]
```

This follows esp-mint's `POST /redeem` as it is built (see "Redemption" in the esp-mint README). Only the service redeems: the request names the service, every input is signed over the request digest with the note's own key, and the whole request is signed with the service's DID key. The wallet builds the mint's canonical binary encoding (`esp_mint::redeem::encode`) and sends it as `application/octet-stream`.

What goes in. `build_redemption` takes every free ESP note for the service whose key is `service_secret` and whose redeemable-after day has come on the wallet's clock (`now_unix / 86400 >= day`). Mixed days are allowed. Notes of other services, and notes not yet mature, are left alone. The memo says where the payout goes (for example `btc:ADDRESS`). It must not be empty or blank and must fit `max_memo_bytes`.

Size and fee. The size is exact: `119 + 186 per input + memo bytes + 81 per output` (decline and refund outputs alike), which is `sp_wire::esp::redeem::encoded_len`. The fee is `size × fee_per_byte`, with the rate taken from `GET /fees` (the `redeem` block, whose size constants the wallet checks against 119, 186 and 81). `RedeemBuild` and `RedeemOutcome` report `size_bytes`, `fee_per_byte` and `fee_esp`, and the command prints them before sending.

Outputs. The accepted value minus the fee comes back as decline outputs, held under each note's own service and day (the mint checks the total against what it owes and each day against what it accepted). The fee is taken from the service and day with the most value first, then the next largest, so small days keep their value. The mint does not fix where the fee comes from: it checks only the total and each day's cap. Amounts over `u64::MAX` are split into several outputs. The output count changes the size and so the fee, so the wallet repeats the sum until it settles. If the notes are worth less than the fee, or the fee would take all of them so that the mint would owe nothing, that request is not sent and the wallet says why (`not sent: ...`, printed by the command). Its notes stay free. When no request is left the result is `NotEnough` with the same reason. `plan_redemption` returns the built requests together with these reasons; `build_redemption` returns just the requests.

Splitting. If the request would be larger than `max_request_bytes` (from `/fees`, or lower with `--max-bytes`), the notes are split, oldest day first, into several requests that each fit, counting the worst case for outputs. Each part is its own request with its own fee and its own payout entry. A ceiling too small for one note is refused.

Crash safety. Each request is stored in the wallet file by its request hash (`sp_wire::esp::redeem::request_hash`, also the mint's entry id) with its exact bytes, and its notes are reserved by that id before it is sent. The blinding factors for its decline and refund outputs are stored with it. After a lost reply or a fault, send the same bytes again: the mint keeps its answers by request hash, so nothing is burned or queued twice. `finish_redemption` can be given the same answer more than once.

Bad proofs. A note the mint rejects for a bad proof (in a reply or in a refusal's totals) stays in the wallet and in the balance, but its id is saved in the wallet file (`bad_proof`) and redemptions no longer pick it. `balance` prints `bad proof N note(s) worth X ESP`. `is_flagged_bad_proof(id)` checks the flag and `clear_bad_proof(id)` clears it.

The answer. Each note gets a decision: accepted, or rejected with a reason (`wrong_service`, `bad_proof`, `already_spent`, `immature`) and whether it was burned. `finish_redemption` removes burned notes, moves `already_spent` notes to the spent record, flags `bad_proof` notes, and frees the rest. Refund outputs the mint signed are unblinded into notes. With an owed amount the message is "payout queued" and the entry is open. When the fee takes everything the message is "nothing owed, fee taken", there is no entry, and the redemption ends.

Refused requests. A `400` or `413` is `WalletError::RedeemRefused { code, why, totals }`. For `refund_required` and `outputs_over_limit` the mint sends its `totals` (each note's decision and the accepted and rejected value by service and day). `rebuild_redemption` drops `already_spent` notes to the spent record, frees `wrong_service` notes, flags `bad_proof` notes (below), and builds a new request from the mint's figures: if the accepted notes cannot pay the fee, the genuine rejected ones (for example, immature on the mint's clock) pay the shortfall and the rest comes back as refund outputs. The old request is replaced. The command does this up to 4 times. Any other refusal frees the notes (`cancel_redemption`). `below_fee` means even all the genuine notes do not cover the fee.

Collecting. A queued redemption stays in the wallet with its notes gone. Sending the same request again returns the entry's state: `open` (nothing to do), `completed` (with the operator's payment reference; the redemption ends) or `declined` (the operator's reason and the mint's signatures on the stored decline outputs, which the wallet unblinds into notes under the original days; the redemption ends). `cancel_redemption` refuses a queued redemption.

### FSP

The decisions behind FSP (the eight answers, the crash ordering, rotation) are in the [fsp-mint DESIGN.md](../fsp-mint/DESIGN.md); this is the wallet's side.

- **Issue.** `build_fsp_issue(service, units, fee_per_byte)` takes the app's free ESP for that service (any days mixed: FSP ignores maturity), groups it by day, makes power-of-two FSP outputs worth the ESP less the fee, and stores the request as pending (notes reserved) before it is sent. `fsp issue` sends it to `POST /issue`.
- **Pay.** `build_fsp_spend(service, units, memo)` picks FSP notes on the current or previous keyset, adds change outputs on the current one, and stores the request. `fsp pay` sends it to `POST /spend`.
- **Crash safety.** Every FSP request is stored with its request hash before it is sent. A crash, a lost reply or a `502`/`409` leaves it pending; the next connection sends the same request again and finishes from the mint's stored answer. A `400` frees the notes.
- **Automatic rollover.** On every connection to an FSP mint, and at startup for every FSP mint the wallet knows, `fsp_sync` reads `/keys`, finishes pending requests, marks notes on a keyset the mint no longer has as lost (kept in `lost_fsp`, shown by `balance`), and swaps every note on the previous keyset for the current one (`build_fsp_rollover`: a spend that pays 0). No prompt. A failure is logged and retried on the next connection. The swap is staggered: each wallet waits its own delay after the rotation, at least a second and at most 0.5% of the period and never more than 72 hours (drawn at random once and kept only until the swap is done; see "Swap times are not kept" below; using the mint's clock from `GET /rotation`), so all wallets do not swap at once. *Why automatic:* a note left on the previous set through the next rotation is lost, and a holder should not have to know about rotation.
- **Lost FSP.** FSP that sat in a wallet that never connected for a full cycle (one to two periods, one to two years by default) cannot be used; the mint has deleted its keyset and its spent list.
- **The window.** `fetch_fsp_rotation` reads `GET /rotation`; `fsp-window` prints it.
- **ESP schedule.** `esp_schedule(service, by)` reads the wallet's own ESP notes (no mint call) and gives what is mature now, what is mature by a date, and a by-month breakdown. It is for the service, which holds the ESP it took in for FSP until it matures.

### Rotation of PSP and ESP

psp-mint and esp-mint rotate the same way (activation 8760 hours after the first issue, period 87600 hours, two key sets and two spent lists). At startup, for `$ECASH_PSP_URL` and `$ECASH_ESP_URL` when the wallet holds that kind, `rotation_sync` reads `GET /rotation`, finishes pending rollovers, marks notes beyond the window as lost, and after this wallet's staggered time swaps previous-set notes with `POST /rollover` (batches of up to 1000 notes; ESP per service and day, keeping both). A failure is logged and retried at the next start. - **Keysets are recorded and named.** The wallet records the keyset of every PSP and ESP note: from the keys a claim was unblinded with, or from the mint's reply to a rollover or hand-over swap. Every PSP request names them (`input_keysets` and `keyset` on `/rollover`, `psp_input_keysets` on the ESP exchange), and the outputs of a swap name the PSP's current keyset, read fresh from `/rotation` at each connection (the cached live keysets are replaced every time, so they cannot go stale). A token carries each note's keyset.
- **ESP keysets.** ESP notes are keyset-addressed too. The wallet reads the ESP mint's live keysets (`GET /keysets`, and `/rotation` on each rotation sync) before an exchange, transfer or redemption, names the current one for new outputs (exchange `keyset`, transfer `keyset`, the redemption's output keyset) and each note's recorded keyset for its inputs (transfer and rollover `input_keysets`, one keyset per redemption input, and `keyset` on each FSP issue note and hand-over note). New ESP notes record the keyset the mint's reply names (transfer, exchange and rollover replies, and each decline or refund signature), which can differ from the one asked for (a queued decline signed after that set retired), and they are unblinded with that reply's keys. A PSP claim is unblinded with the keys of the keyset the PSP printed, from `GET /keysets`, never the current set by assumption. A redemption without a known current ESP keyset is refused locally ("connect to the mint first").
- **The keyset is remembered for each pending request.** A pending exchange, transfer, redemption or rollover keeps the keyset its outputs name. Mints sign with whichever live keyset (current or previous) a request names, so a request built before a rotation is sent as it is and the reply names the keyset that signed. If the named keyset has been deleted since (two rotations), the mint refuses `keyset_retired` before burning anything, the wallet frees the notes, and the request is built again from a fresh read of the keysets. There is no re-blinding step.
- **No keyset guessing.** Every note the wallet stores records its keyset (from the reply that signed it, the PSP claim, or the hand-over or handoff that brought it). A note without one is refused with "note X has no recorded keyset, so it cannot be spent"; it is not picked for rollovers. A hand-over note without a keyset is refused (a handoff cannot hold one: its format requires a key set for every note), and a mint reply that names no keyset is not stored. Redemption sizes are now `119 + 186 × notes + memo + 81 × outputs` (format version 2); exchange `48 + 146 × notes + 41 × outputs`, transfer `120 + 146 × notes + 41 × outputs`.
- **A note claimed on the current set after a rotation is not rolled over.** The rollover picks notes by their recorded keyset (any but the current set); a note with no recorded keyset is never picked.
- **Expired notes are written off with a message.** A note whose recorded keyset is neither current nor previous was retired: it is moved to `lost` (not in the balance), and the sync says "N note(s) expired: their key set was retired at a rotation before they were rolled over". Claim signatures printed for a retired keyset are refused with a message saying the outputs expired. A mint's `unknown_keyset` answer means junk or the wrong mint, not expiry.

- **Swap times are not kept (privacy).** Each rotation's swap time is a random delay (at most 0.5% of the period, capped at 72 hours, from the mint's clock) drawn once and stored in `swap_schedule`, for FSP, PSP and ESP alike. It is deleted in the same atomic write that records the new notes when the rotation's last batch completes, and the whole entry is dropped when the old set retires. No history is kept, and the logs never print a swap time.

### Handing PSP to another wallet

For a developer that sells PSP to its users by in-app purchase, with this wallet inside the app. There is one way to do it, the PSP handoff (next section). The older `send-psp` token (`send.rs`, `psp1`, `receive-psp`, `sent`) was removed in 0.5.0: it did the same job with a bearer token that was not encrypted. What was worth keeping moved into the handoff: the reclaim and the check. *Why always a swap at the mint:* a developer who double-spends only hurts its own users, but the swap costs almost nothing and protects against accidents such as a wallet restored from an old backup or a bug that reuses notes. ESP and FSP still always go through their mints.

- **Reclaim and check (the sender).** An outgoing PSP handoff keeps the notes and the PSP mint (`OutgoingHandoff { notes, mint, reclaim, spent_elsewhere }`). `http::check_handoff` asks `POST /check-state` for the nonces: none spent leaves it `Pending` (`Standing::Pending`); all spent ends it as `Done` and drops the notes (`Standing::Received`); some spent drops those notes, counts them in `spent_elsewhere` and leaves the rest reclaimable (`Standing::Partly`). `http::reclaim_handoff` stores a swap of what is left back to this wallet (`Wallet::begin_reclaim`, tag `reclaim|<id>`, the handoff's `reclaim` field points at it) and sends it. The mint takes the first swap that reaches it, so the record at the mint decides: if the receiver was first, the mint refuses (`note_spent_elsewhere`), the stored swap is dropped, the handoff stays pending and the next check finds the notes spent; if the sender was first, the handoff ends as `Reclaimed` and the fresh notes are in the balance. The stored swap's outcome and the handoff's state change **in the same write** (`finish_rollover`, `cancel_rollover` and `mark_spent_in_rollover` call `handoff::settle_reclaim` inside their own `update`), so a crash cannot leave a finished reclaim recorded as pending. A repeat of the request gets the mint's stored answer by request hash.
- **No lock on unswapped notes (the receiver).** Before 0.5.0 a received PSP handoff was held only inside its stored swap, in no balance and unspendable, because `send-psp` could pass such notes on without swapping them. With `send-psp` gone the lock bought nothing: a note spent at the mint is burned just like a swapped one, so whichever of the swap and the spend reaches the mint first wins and the other is told. Now the import adds the notes to `notes` (with their key sets recorded) and stores the swap beside them, unreserved. The swap is sent first thing whenever the mint answers: `http::complete_import` on import, then `rotation_sync`, which sends stored swaps before anything else, at startup and on every connection. `Balance::psp` counts them; `Balance::unswapped_psp` says how much of it is still waiting.
- **Keeping the stored swap true.** The swap names its inputs, so a note spent here since (handed on, exchanged) would make the mint refuse the whole request. `send_rollover` first calls `Wallet::live_swap`, which replaces the stored swap by one for the notes still held and free (or drops it if none is). `prepare_rollover` leaves notes that are inputs of a stored received swap out of the ordinary rollover. When the mint does refuse with `note_spent_elsewhere` (the sender reclaimed first, or a copy was received first), `Wallet::swap_found_spent` moves the named notes to the `spent` record, so they leave the balance (they were never this wallet's), and the swap is rebuilt for the rest and sent again; the mint reports one spent input per refusal, so this repeats until the rest is swapped. Any other refusal drops the stored swap and leaves the notes in the balance as they are.
- **Old records are migrated on load.** The `sent` list of a wallet file from 0.4.0 or earlier is read into `legacy::SentToken` and turned into `OutgoingHandoff` records by `WalletData::migrate_legacy` when the file is opened and when two copies are merged (the table is in `legacy.rs`). *Chosen over keeping a second kind of record:* one set of commands, one set of states, nothing to maintain twice, and the stored `reclaim|<id>` swap that `sent --reclaim` made uses the same tag, so a reclaim that was stored and not sent finishes through `handoff check`. The cost is that a record is rewritten the first time the file is saved. A stored `receive|<id>` swap is still sent at the next sync, but its notes cannot be counted (the wallet holds the signed request, not their secrets).

### Handoff, merge and the service ID

Three pieces that let value and identity move between wallets without the AIR (`src/handoff.rs`, `src/merge.rs`, `src/store.rs`). *Why:* an unfunded wallet cannot pay to read from the AIR, so a new device or user needs its first notes, and its identity, from another device or from an app. And a wallet restored from storage may be older than the one on the device.

**Handoff: exactly two kinds.** (`src/handoff.rs`.) v0.4.0 had one combined handoff (PSP, FSP and an optional DID key, swap optional), which let you build combinations that make no sense: a PSP handoff with a DID key, unencrypted, or unswapped; an FSP handoff swapped. That was a bug, so the combined kind is gone and there are two, each with its own types, string prefix and import:

- **PSP handoff** (`SPHP1:`), a developer to a user. `PspPayload { mint, notes }` has no field for a DID key or FSP. `export_psp_handoff(ids, psp_mint, recipient)` needs the recipient's DID public key and seals the body to it with `sp_wire::seal::encrypt` (AIR's `PublicKey::encrypt`; sp-wire's module is the one place that wraps it, so nothing new was written and the format of what is sealed is the mint payload's). `import_psp_handoff(text, key, from)` opens it with the DID secret key, adds the notes to `notes` and **always** stores a PSP swap (`POST /rollover`) in the same write as the import record; there is no parameter to skip it. The swap is stored under the tag `handoff|<id>|<n>` and sent at once by `http::complete_import`; if the mint cannot be reached it stays in `pending_rollovers`, `Balance::unswapped_psp` (and `balance`) shows the units still waiting, and `rotation_sync` sends it on every connection to the mint and at every start (see "Handing PSP to another wallet" for why the notes are not locked meanwhile, and what happens when the mint refuses).
- **FSP handoff** (`SPHF1:`), a user's old device to the new one. `FspPayload { groups, did_key }` has a non-optional DID key and at least one group; `export_fsp_handoff(ids, did_key)` takes FSP notes only. It is not encrypted, because it carries the key it would be encrypted to. `import_fsp_handoff(text, from)` adds the notes as they are and returns the DID key for the caller to keep (the wallet does not); there is no swap, since both devices are one owner's. After the AIR fetch (not built) `merge FILE` unites the small wallet with the fetched one.

Why the prefixes differ (`SPHP1:`, `SPHF1:`): the kind decides what is checked and how it is opened, so it must be known before any parsing, and a string of one kind can never parse as the other (the two bodies also start with a kind byte, 0 and 1, and a PSP body is refused if anything follows its notes). `kind_of(text)` tells a caller which key a string needs before it imports. The old `SPH1:` is refused with a message naming the new kinds (keeping it was not trivial: its meaning was the thing that was wrong). Old `handoffs_out` and `handoffs_in` records read as kind `combined` and are kept.

- **Bearer secret.** Both strings hold every note's spend key; the FSP one also the DID key. `PSP_WARNING` and `FSP_WARNING` are printed on standard error by every export and every import. The README and the module docs say it too.
- **Versioned, checked, bounded.** A version byte (1), a 4-byte SHA-256 check (of the sealed bytes for PSP), at most 1000 notes, every amount a power of two, and every spend secret must match its note's nonce. A damaged payload, another version or kind, a forged secret or a key set that is retired is refused with a message before anything is added. A note's signature can only be checked by the mint, so a note is known good only once it is swapped or spent (the command line then reads the FSP mints' keys, which moves notes on a retired set to the lost record).
- **Validated against what the wallet knows.** The key sets of a mint whose live sets the wallet has seen must still contain the note's set; for FSP the service and its mint are looked up. What the wallet has not seen cannot be checked, and the import says so in its warnings.
- **The id** is the first 16 bytes of SHA-256 of the unsealed body, so the sender and the receiver both have it, and it does not change with the seal's fresh key. **Double import:** refused by the id and by note: a note already held, or one that was held and has left (spent, handed off, lost), is never added again. A wallet also refuses to import a handoff it made itself.
- **Source.** Each imported note's id is listed in `handoffs_in` with the handoff id, its kind and the sender's name if given.
- **Cancel.** `cancel_handoff` puts the notes back and is local only; it is refused while a reclaim is stored (that one may already have reached the mint). For a PSP handoff the receiver swaps at once, so after a cancel the first of the two to swap or spend wins and the other learns from the mint: use `handoff reclaim` instead, which lets the mint decide before the notes come back. For an FSP handoff the receiver holds the same secrets until one of them spends, and the mint has no record of who holds an FSP note, so cancel is all there is. `finish_handoff` drops the notes once the sender knows it was claimed.
- **`send-psp` is gone.** The PSP handoff replaced it (above, "Handing PSP to another wallet").

**Reconcile.** `merge(local, stored)` unites a wallet retrieved from storage with the local one, in either direction and any number of times (the result is the same). `Wallet::merge_from` writes it atomically, and writes nothing if nothing changed. The wallet file has a `version` counter, up by one on every write, and the merge keeps the larger. Rules:

- **Notes are united by identity** (the nonce). A note that is gone in either copy stays gone: it is in `spent`, `lost`, `lost_fsp`, a handover or a pending handoff, or the ledger below says it left. (Old `send-psp` records are turned into handoff records in both copies before the merge, so they are handled as handoffs.) A done or reclaimed handoff wins over a pending copy of it. A note held in only one copy is added if it is not gone, which is how a new device receives the starter notes of the old one.
- **The ledger.** A tombstone set cannot say that a note was cancelled back into the wallet, so the file counts departures and returns: `departed[id]` goes up each time a note leaves `notes` and `returned[id]` is set equal to it when the note comes back. A note is gone when `departed` is larger than `returned`. The counters are kept by `update` (`track(before, after)`), so no code path needs to remember them; the merge takes the larger of each. Cost: about 70 bytes of file for each note that ever left.
- **Requests.** Pending purchases, exchanges, transfers, redemptions, FSP requests and rollovers are united by request id without duplicates. The `finished` set lists request ids that ended, so a stale copy cannot bring a finished request back, and a note reserved by a request is reserved by it in the result.
- **Maps** (key sets, epochs, the live key sets, FSP mints, swap schedule) are united with the local entry winning on a conflict.
- The merge never adds a note the ledger says left, never drops a note both copies hold, and never turns a spent note back into a held one.

**The service ID on FSP notes.** An FSP note's service is stored in its `terms.service` (with day 0), as for ESP, and is not part of what the mint signs: no wire change. `StoredNote::fsp_service()` reads it; `balance()` groups FSP by service (`Balance::fsp_by_service`) and spending, the rollover and the handoff work by service. fsp-mint's `GET /keys` and `GET /health` already report the service, and the wallet fills `terms` from them for notes that came from a rollover or a reply. A wallet file from before this release is migrated at startup (`fill_fsp_services`): a note with no service gets the service of the one FSP mint that has its key set as current or previous, and when no mint has it, or two do, the note stays `unknown` and is shown that way in `balance` with a hint. Nothing is guessed.

### Settings and the storage policy

The wallet's first settings with a file (`src/config.rs`, the same shape as the mints': `SPECS`, an unknown key or a bad value refused with every problem listed, defaults then file then environment). `config.toml` sits beside the wallet file, or is named by `--config` or `$ECASH_CONFIG`; `ecash-wallet config` prints the values in use and where each came from.

The settings are the **storage policy**: `storage.wallet` and `storage.app`, each an ordered list of service IDs (index 0 the primary, the rest secondaries). The parser and the checks are `sp_wire::storage`, shared with the three mints (`storage.mint_state`), so a list means the same in all four: 64-hex x-only keys (a 33-byte DID key is reduced to one), at most 8, no duplicates, no empty entry; one entry is valid (one service and a local backup copy); empty means local only.

*Why the primary is the fee service.* The wallet pays FSP fees for storage to a service. Which one has to be a decision of the policy, not an accident of the notes the wallet holds: a wallet that holds FSP for three services would otherwise pay storage fees to whichever it picked. `Settings::storage_service()` is the primary of `storage.wallet`; the `fsp` commands default `--service` to it, and say so; with the list empty there is no storage service and `--service` is needed. `balance` shows the FSP held for it.

Config and validation only: nothing reads or writes the AIR. The wallet file is still the local file, with its `version` counter and `merge` for the day a copy comes back from storage. What the storage must provide is listed in the mints' DESIGN.md files ("Storage policy"): the wallet file is the one that carries a version and is merged (requirement 5 there).

### The reply DID

`build_psp_payload` takes the reply DID from the caller. The command line uses a stand-in, a made-up 33-byte key kept in the wallet file (`reply_did`), until a wallet has a real AIR identity. The PSP mint treats the field as opaque bytes, and the signatures are not delivered to it yet (see ROADMAP.md in sandbox-mint).

## Tests

`cargo test` runs:

- **Blinding.** An unblinded signature verifies against the mint's key. A wrong key or wrong blinding factor does not.
- **Note file.** A change is saved before the call returns. A reopened wallet has the same notes. A corrupt file is an error and is not replaced. The file is `0600`.
- **PSP.** A payload round trip: build, decrypt with the mint's key, decode, and the outputs match. A payload sealed to another key does not decrypt. Claimed signatures become notes the PSP accepts. A partial claim leaves the rest pending. A signature cannot be claimed twice. A bad claim changes nothing. The denomination and output-count limits.
- **ESP.** The request is always exact: the PSP notes spent, times 10^11, equal the outputs' total, with and without change. The cover is the exact set when one exists and otherwise the tightest the wallet can find, checked on several holdings. The memo and request hash match the ESP mint's. Spend signatures cover the memo. A refused exchange frees the reserved notes. A finished one swaps PSP notes for ESP notes, change included. The asked-for split must add up. Not enough PSP, and an exchange below 1 PSP, are refused before anything is reserved. **Spent elsewhere.** `mark_spent_elsewhere` moves the notes the mint names out of the balance into the spent record and frees the others, survives a reopen, leaves them out of later exchanges, and changes nothing when the mint names no note, a position the request lacks, or an exchange the wallet does not have. `exchange_refusal` reads the mint's `400` body: the spent-elsewhere answer carries the positions, and every other `400`, or a body that does not say so, is an ordinary refusal.
- **`tests/flow.rs`, in one process, with no network.** Build the payload, reopen the wallet, open the payload as the mint does, settle it with the PSP's real settlement code, read the printed signature lines, claim, check every note with the PSP's own check, then exchange against the ESP mint's real exchange code: 3 PSP from a 4 and a 1 (the 4 is spent, 3 PSP of ESP plus 1 PSP of change), a request made one ESP unit off is refused before anything is burned, and the last 1 PSP is exchanged exactly. Every ESP note, change included, is checked against the key the mint derives for its terms. A retry gets the same reply and burns nothing more. Also: a payload sealed to another key is ignored and leaves no record, a payload with any one byte flipped is ignored, an exchange without enough PSP is refused before anything is reserved, and a signature the wallet did not ask for is refused.
- **Transfer** (`src/transfer.rs`). The hand-over picks an exact set, refuses an amount no set adds up to, and prefers the notes of one service and one day. It refuses a day when the wallet holds several and none is named. Receiving checks each spend secret against its note and refuses a duplicate. A transfer request is signed by the service and by every input, and the signatures match the ESP mint's digest. The wallet with no matching key, or none for that service, builds nothing. New sizes must add up to the old total. A finished transfer swaps the notes and checks each new note against the mint's key. A reply with a wrong total, a wrong signature or the wrong number of notes changes nothing. A cancelled transfer frees the notes. A pending transfer survives a reopen and can be resumed.
- **`tests/fsp_flow.rs`, in one process, with a real esp-mint and fsp-mint over local HTTP.** Issue FSP from ESP of mixed days, pay with change, the automatic rollover after a rotation (staggered, then swapped without a prompt), a crash after the mint answered finished from the stored answer, offline within the window rolls over and beyond it is lost, a failed rollover logged and retried on the next connection, and the ESP schedule.
- **`tests/transfer_flow.rs`, in one process, with no network.** Buy 5 PSP as a 4 and a 1 and settle. Exchange 3 PSP and then 1 PSP, which gives ESP notes of 3, 1 and 1 PSP. An inexact hand-over is refused. Hand over 3 PSP, receive it as the service, build the transfer and run the ESP mint's real transfer code. The mint's supply is unchanged, a retry gets the same reply, and the new note verifies against the mint's key. Presenting the same notes again is refused as already spent, and cancelling frees them. A different service key finds nothing. The new note can be split into 1 and 2 PSP. A reopened wallet equals the one in memory.
- **Spent notes the mint names** (`src/redeem.rs`, `src/transfer.rs`, `src/rotate.rs`, `src/http.rs`, `tests/redeem_flow.rs`). `refuse_redemption` moves the notes a `below_fee` refusal calls `already_spent` to the spent record, flags a bad proof, frees the rest, and with no list just frees the notes. `mark_spent_in_transfer` and `mark_spent_in_rollover` do the same for the positions the mint names, and refuse a position the request lacks. The refusal bodies are read (`redeem_refusal`, `exchange_refusal`, and the rollover reader, with no stray `: ` when the mint sends no code). `tests/redeem_flow.rs` runs it against a real esp-mint: a copy of a spent note is refused `below_fee`, moved to the spent record, and not offered again.
- **Single error print** (`src/main.rs`). A failed redemption request is printed once, by `main`; later failures get their own line.
- **Handoff** (`src/handoff.rs`, `tests/handoff_flow.rs`). The base-44 codec round-trips every length and uses only the QR alphanumeric characters. A PSP handoff is sealed to a DID key and round-trips; only that key opens it (another key is refused with nothing written); an unsealed one, one with a DID key or FSP in it, and an FSP body under the PSP prefix are refused. An FSP handoff with two services and a DID key round-trips, adds the very notes the sender held, and is never swapped; a body without its DID key, without groups, with bytes after the key, or a PSP body under the FSP prefix is refused. A string under the other kind's prefix is refused, as is the old `SPH1:`. Export refuses the wrong kind of note for each handoff, a note twice, nothing, an inexact amount and a held-back note. Sizes are as documented. Whitespace and case are forgiven; a damaged, cut or extended payload, another version, a forged secret, a retired key set, a non-power-of-two amount and a second import are refused with nothing added. Cancel returns the notes; done drops them. `tests/handoff_flow.rs` runs it against a real psp-mint (a PSP handoff opened with the right key only, swapped and final; the same string refused by the mint a second time; cancel; **a swap that cannot be sent leaves the PSP unswapped but in the balance and spendable, and the next sync swaps it; a note spent before the swap is sent is left out of it and the rest is swapped; reclaim before the receiver swaps (the sender gets fresh notes, burns the handed-off ones, and a late receiver is told they are spent and loses them from the balance), reclaim after the receiver swapped (nothing comes back, the handoff is done), a note spent elsewhere (check says partly, the rest is reclaimed, and a receiver drops the spent one and swaps the rest), and records `send-psp` left in an old wallet file (pending, received, reclaimed, and a stored reclaim that is finished by `handoff check`)**) and a real esp-mint and fsp-mint (FSP and a DID key to a wallet that has never seen the mint, not swapped, grouped by service, and spent at the mint).
- **Merge** (`src/merge.rs`). The version counter goes up on every write. Two diverged copies are united in both directions with the same result. A stale copy cannot revive a spent, lost or handed-off note, and a cancelled handoff comes back. A new device receives the starter notes. Pending requests are united once; a finished request is not revived. Merging a wallet with itself changes nothing and writes nothing.
- **Settings** (`src/config.rs`). The defaults are local only and round-trip through `get` and `set`. The file is read, then the environment wins, each value with its source. A named file must exist and `--config` beats `$ECASH_CONFIG`. A list in the file is an array or one string; an empty list is local only. A duplicate, an empty entry, a bad key, a number in the list, an unknown setting and bad TOML are each refused, all listed together. The storage service is the primary of `storage.wallet`, not of `storage.app`.
- **Wire version** (`src/http.rs`). A mint that reports another `wire_version`, or none, or one that is not an integer, is refused with a message naming both numbers and saying nothing was sent. The version is checked before the network. A matching mint passes. `src/date.rs` has the date parser's known answers and refusals.
- **Note limits** (`src/esp.rs`, `src/http.rs`). The exchange limit is the mint's, read from `/fees`; with none read the wallet checks nothing of its own.

The regtest runs in [REGTEST.md](REGTEST.md) are the end-to-end tests with a real Bitcoin node.

## Command line behaviour

On a `400` the exchange or transfer frees its notes. The exception is a request the mint says had notes spent by a different request: those notes are marked spent (they leave the balance and `balance` prints "spent elsewhere N note(s)"), and the request's other notes are freed. The mint names them in the refusal (`code: note_spent_elsewhere`, `spent`: positions in the request) on an exchange, a transfer and a rollover (PSP and ESP). A redemption refused for being `below_fee` carries a reason for every note (`notes`), and the wallet moves the notes marked `already_spent` to its spent record, flags the ones marked `bad_proof`, and frees the rest. On any other failure it keeps the request and prints the `--resume` command.

**Note limits.** The wallet holds no limit of its own for ESP, and none for the largest PSP note: `buy-psp --psp-url` reads the PSP's top denomination from its `GET /keys` (the highest amount with a key, `http::sync_psp_limits`) and refuses a larger size; offline it checks only that the size is a power of two and the PSP decides the top. Before an exchange or a transfer it reads `exchange.max_items` and `transfer.max_items` from the ESP mint's `GET /fees` (`http::sync_esp_limits`) and refuses a request over them, naming the mint's setting. Offline it builds the request and lets the mint decide. The one count the wallet does hold is `psp::MAX_OUTPUTS`, 255 outputs in a purchase: that is not a setting but the payload format, whose output count is one byte.

*Why mainnet by default:* the default should be the network a real user is on; development passes a flag.
